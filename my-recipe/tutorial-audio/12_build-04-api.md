# 音声版 12章 ステップ4 サーバー側の処理を作る まずは偽レシピで

この章のゴールは、ブラウザと自分のサーバーの間の通信を完成させることです。
返すレシピは、まだ偽物です。AIは次のステップで繋ぎます。

## なぜAIを繋ぐ前に、偽物で通すのか

いきなりAI連携まで書くと、動かなかったときの原因候補が、8つもあります。

1つめ、fetchのURLが間違っている。
2つめ、POSTのボディの形が違う。
3つめ、ルートハンドラーが正しく作れていない。
4つめ、環境変数が読めていない。
5つめ、APIキーが間違っている。
6つめ、Claude APIの呼び方が違う。
7つめ、返ってきたJSONの形が想定と違う。
8つめ、画面側の受け取り方が違う。

8個の容疑者を一度に相手にするのは、初心者には無理です。

偽レシピを返すAPIで、先に、1番、2番、3番、8番を潰しておけば、
次のステップで動かないときの容疑者は、4番から7番の4つに絞れます。

この、一度に1つのことだけ変える、という進め方が、
デバッグの世界では、最も強力な武器です。覚えておいてください。

## ルートハンドラーを作る

appフォルダの中の、apiフォルダの中の、generate-recipeフォルダに、
routeというファイルを作ります。

中身は、まず、ダミーのレシピを定数として定義します。
ここにも、ステップ5でClaude APIの呼び出しに差し替える、とコメントを書いておきます。

そして、POST、という名前の非同期関数をエクスポートします。
中では、リクエストのJSONを読んで、コンソールに出力し、
ダミーのレシピをJSONで返すだけです。

これだけで、スラッシュ・エーピーアイ・スラッシュ・ジェネレート・レシピ、
というAPIができました。

### 確認方法その1 ブラウザでは直接叩けない

このURLをブラウザで開くと、405、メソッド・ノット・アラウド、というエラーが出ます。

これは正常です。
ブラウザでURLを開くのはGETですが、
このファイルにはPOSTしか用意していないからです。1章の話ですね。

### 確認方法その2 curlで叩く

ターミナルから、curl、カールというコマンドで、直接POSTしてみます。
メソッドにPOSTを指定し、ヘッダーでJSONを送ると宣言し、
データとして食材とジャンルのJSONを渡します。

レシピのJSONが返ってくれば、成功です。

そして、npm run dev を動かしているターミナルに、
サーバーが受け取った内容、として、送った中身が表示されているはずです。

ここで、非常に重要なことがあります。
console.log が、どこに出るか、です。

クライアントコンポーネントに書いたログは、ブラウザのコンソールに出ます。
ルートハンドラー、サーバーアクション、サーバーコンポーネントに書いたログは、
ターミナルに出ます。

これを知らないと、ログが出ない、と言って、何十分も溶かします。
サーバー側のコードはブラウザで動いていないので、当然、ブラウザには出ません。

## サーバー側でもバリデーションする

ステップ3で、ブラウザ側のチェックは書きました。
サーバー側にも、同じものを書きます。

理由は、5章と8章のおさらいです。
ブラウザのコードは、利用者が書き換えられます。
さらに、さっきのcurlのように、画面を通さずに直接APIを叩くこともできます。

つまり、フォームで10個に制限したから安全、は成立しません。

サーバー側の処理は、3段階です。

### 1段階目 JSONとして読めるか

リクエストのJSONを読む処理は、
送られてきたものがJSONでないと、例外を投げます。

try、catchで囲まないと、サーバーが500エラーを返してしまいます。
壊れたリクエストが来たのは、クライアントのミスなので、400を返すのが正しいです。

そして、受け取る変数の型は、unknownにします。
何が入っているか、保証が無いからです。

### 2段階目 中身を安全に取り出す

まず、食材の項目が配列かどうかを確認します。

配列なら、中身のうち、文字列で、かつ空白だけでないものだけを残します。
配列でなければ、空の配列として扱います。すると、次のチェックで400になります。

こうしておけば、食材のところに文字列が入った、変なリクエストが来ても、
エラーで落ちずに、きちんと400を返せます。

### 3段階目 業務ルールのチェック

食材の数がゼロなら、食材を1つ以上入力してください、を400で返します。
10個を超えていたら、食材は10個までにしてください、を400で返します。

### ジャンルはホワイトリスト方式

ジャンルの扱いには、別の関数を用意します。

受け取った値が文字列で、かつ、7つのジャンルの配列に含まれていれば、そのまま使う。
含まれていなければ、こだわりなし、に倒す。

ここが設計判断です。
ジャンルが変な値でも、レシピ生成自体は問題なくできるので、
エラーにする価値がありません。
一方、食材が空なら、生成のしようがないので、エラーにします。

つまり、エラーにするか、安全な既定値に倒すか、は、
処理を続けられるかどうかで決める、ということです。

なお、許可するものを列挙するこのやり方を、ホワイトリスト方式と呼びます。
セキュリティの基本形です。
逆の、禁止するものを列挙するブラックリスト方式は、必ず漏れが出ます。

## 画面からAPIを呼ぶ

ページの generate 関数を、本物の通信に差し替えます。処理の流れはこうです。

まず、生成中フラグをtrueにして、前回のエラーを消します。

そしてtryの中で、fetchでAPIを呼びます。
メソッドはPOST、ヘッダーでJSONを送ると宣言し、
ボディには、食材とジャンルを、ストリンギファイで文字列にして入れます。

返ってきたレスポンスに対して、jsonメソッドでオブジェクトに戻します。

もし、レスポンスのokがfalseなら、
サーバーが返してきたエラーメッセージを表示して、早期リターンします。
サーバーが何も返してこなかった場合に備えて、null合体演算子で既定の文言を用意します。

成功したら、レシピをstateに入れ、食材とジャンルも保存します。

catchでは、レシピの考案に失敗しました、というメッセージを立てます。

そして、finallyで、生成中フラグをfalseに戻します。

あわせて、エラー用のstateを追加して、画面に表示するようにします。

### finallyが効く理由

finallyは、成功しても、失敗しても、途中でreturnしても、必ず実行されます。

これをtryの最後に書いてしまうと、エラー時に実行されず、
ボタンが、考案中、のまま永久に固まります。
初心者が必ず一度は作るバグです。

### catchが捕まえるもの

catchに来るのは、そもそも通信ができなかったときです。
ネットが切れている、サーバーが落ちている、といった場合です。

ここが重要です。
サーバーが400や500を返した場合は、catchに入りません。

fetchは、返事が返ってきた時点で、成功扱いだからです。
だから、レスポンスのokのチェックが、別に必要になるのです。

これは非常によくある誤解です。
fetchは、返事が返ってくれば、内容がエラーでも成功扱い。
こう覚えてください。

## 二重のバリデーションを、実際に確かめる

ブラウザ側のチェックをすり抜けても、サーバーが止めることを確認します。
curlで、4つのパターンを送ってみます。

1つめ、食材が空の配列。
食材を1つ以上入力してください、が返ってくるはずです。

2つめ、食材が11個。
食材は10個までにしてください、が返ってくるはずです。

3つめ、そもそもJSONですらない文字列。
リクエストの形式が正しくありません、が返ってくるはずです。

4つめ、食材が配列ではなく文字列。
食材を1つ以上入力してください、が返ってくるはずです。

4つとも、サーバーが落ちずに、きちんとメッセージを返せば、合格です。

これは、立派なテストです。
19章の試験では、こういう、
異常な入力を与えて、期待通りのエラーが返るかを確認します。

## Networkタブで通信を見る

F12を押して、ネットワークタブを開いたまま、画面から送信してみてください。

見るところは5つです。

generate-recipe、という行があるか。リクエストが飛んでいるかどうかです。
ステータス。200番か400番か。
ペイロード、あるいはリクエスト。送った内容が正しいか。
レスポンス。返ってきたJSON。
タイミング。どれくらい時間がかかったか。

動かない、と思ったら、まずここを見てください。

そもそも行が出ないなら、fetchが呼ばれていません。ボタンの繋ぎ忘れです。
404なら、URLが間違っています。
400なら、送っている中身が想定と違います。
500なら、サーバー側のコードが落ちています。ターミナルを見ましょう。

この切り分けができるようになると、
独力で進める速度が、何倍にもなります。

## この章のまとめ

AIを繋ぐ前に、通信だけを先に完成させます。容疑者を減らすためです。

appの中のapiの中に、ルートのファイルを作り、
POSTという名前の関数をエクスポートすれば、APIができます。

console.logは、サーバー側ならターミナルに出ます。

バリデーションは、ブラウザとサーバーの両方に書きます。サーバー側が本命です。

外から来たデータはunknownで受けて、確認してから使います。

エラーにするか既定値に倒すかは、処理を続けられるかで決めます。

fetchは返事が返れば成功扱い。レスポンスのokを必ず確認します。

finallyで、処理中フラグを必ず戻します。

詰まったら、ネットワークタブと、ターミナルを見ます。

現時点で、アプリは、食材を送ると、いつも同じレシピが返ってくる状態です。
次のステップで、この最後の1か所を、本物にします。
