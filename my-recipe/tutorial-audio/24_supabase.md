# 音声版 24章 Supabase データベースは何をしてくれているのか

この章のゴールは、Supabaseが何の集合体なのかを理解し、
キーの種類、RLS、ダッシュボードの各画面の意味を、
説明できるようになることです。

## Supabaseは PostgreSQL と周辺装備

Supabaseの正体は、PostgreSQL、ポストグレスというデータベースです。

それに、Webアプリで必要になる装備を足して、
ブラウザから使える形にしたもの。これがSupabaseです。

中心にPostgreSQLがあり、そこにテーブル、行、列、そしてRLSがあります。
その周りに、4つの装備が付いています。

REST API。テーブルをHTTPで読み書きできるようにするものです。
Auth。ログインとユーザー管理です。
Storage。画像などのファイル保管です。
Realtime。データの変化を即座に画面へ通知するものです。
そしてもう1つ、Edge Functions。サーバー処理です。Vercelと同じ役割ですね。

マイレシピで使うのは、PostgreSQL本体と、REST APIだけです。

Authは、意図的に使いません。要件定義の3.3節の判断です。
Storageも、Realtimeも、Edge Functionsも、使いません。
Edge Functionsについては、Next.js側でやるからです。

使わない、を明示できているのが、設計をした証拠です。

Supabaseは多機能なので、全部使おうとすると複雑になります。
必要なものだけ使う、という判断が大事です。

## 実はデータベースに直接繋いでいない

ここは、多くの人が誤解しています。

SupabaseのJavaScriptクライアントを使ったコードは、
データベースに直接接続していません。

実際に起きているのは、普通のHTTPSリクエストです。

テーブルから全件を選択する、というコードは、
内部で、そのプロジェクトのURLの、レスト・スラッシュ・ブイワン、
という階層の下にある、テーブル名のパスへの、GETリクエストに変換されます。

そしてヘッダーに、APIキーが付きます。

Supabase側では、PostgREST、ポストグレストというソフトがそれを受け取り、
SQLに変換して実行します。

このPostgRESTが、テーブルを自動的にWeb API化しているわけです。

テーブルを作った瞬間に、そのテーブルのAPIができあがる。
これが、Supabaseの核心です。

### なぜこれを知っておく必要があるか

4つのことが、腑に落ちるからです。

ブラウザから直接データベースを呼べる理由。
HTTPSだからです。データベースの生のプロトコルは、ブラウザからは話せません。

anonキーが公開されてよい理由。
キーは、誰として話すか、の宣言にすぎず、権限はRLSが決めるからです。

F12のネットワークタブに出る理由。
ただのHTTP通信だからです。

502や504が出ることがある理由。
間にWebサーバーがいるからです。

なお、将来Prismaなどの、ORMを使うときは、
PostgRESTを経由せず、データベースに直接接続する、別の経路を使います。

そのときは、接続文字列が必要になり、扱いがまったく変わります。
こちらは、絶対に公開できません。

## キーの種類 一番大事な話

Supabaseのキーは、2種類あります。
名称が新旧で違うので、両方覚えてください。

1つめが、パブリッシャブルキー。旧称は、anonキー、あるいはパブリックキーです。
これは、公開してよいキーです。ブラウザに置いてもOKです。

2つめが、シークレットキー。旧称は、サービスロールキーです。
これは、RLSを全部無視できるキーです。
サーバーのみで使い、絶対に公開しません。

### なぜパブリッシャブルキーは公開してよいのか

このキーが意味するのは、
私はログインしていない人です、という名乗りだけです。
権限は一切含まれていません。

整理すると、
キーは、私はanonという役割です、という名乗り。
RLSは、anonという役割の人は何をしてよいか、という権限。

権限は、RLSのほうにあるのです。

RLSが正しく設定されていれば、キーが漏れても被害は限定されます。

逆に言えば、RLSを無効にしたままキーを公開したら、
全データが読み書きし放題です。

マイレシピは、RLSは有効だが、全部許可、という設定です。
つまり、キーを知る人は誰でも、お気に入りを読み書きできます。

これは要件定義の3.3節で、承知のうえで受け入れた制約でした。

### シークレットキーは何が危険なのか

RLSを完全に無視します。

どんなポリシーが設定されていても、
全テーブルを読み書き、削除できます。管理者の合鍵です。

絶対にやってはいけないことが、5つあります。

ブラウザ側のコードに書くこと。
ネクスト・パブリックの接頭辞を付けること。
GitHubにコミットすること。
ログに出力すること。
そして、他人に見せること。画面共有も含みます。

マイレシピは、シークレットキーを一切使いません。
使わなければ、漏らす心配もありません。

必要ないものは取得しない、使わない。
これも、立派な安全対策です。

### キーが漏れたときの対処

セッティングスの、APIキーズの画面から、キーを再生成します。
ローテートと言います。

古いキーは即座に無効になるので、環境変数の更新を忘れずに。

漏れたかもしれない、と思った時点で、迷わず再生成してください。
様子を見る理由が、ありません。

## RLSを、もう一段深く

14章では、常に許可、のポリシーだけ書きました。仕組みを理解しておきます。

### ロール 役割

Supabaseにアクセスするとき、あなたは必ず、何かの役割を名乗っています。
3つあります。

anon。ログインしていない人。
authenticated。ログイン済みの人。
service_role。管理者です。RLSを無視します。

### ポリシーの構造

ポリシーは、5つの要素でできています。

ポリシー名。
どのテーブルに対してか。
どの操作種別に対してか。セレクト、インサート、アップデート、デリート、またはすべて。
どのロールに対してか。省略すると、全ロールです。
そして、条件です。

条件には、2種類あります。
usingと、with checkです。

### usingとwith checkの違い

ここは、必ず混乱するところです。整理します。

usingは、セレクト、アップデート、デリートのときに評価されます。
対象は、既にある行です。その行を見てよいか、を判定します。

with checkは、インサート、アップデートのときに評価されます。
対象は、これから書き込む行です。その行を作ってよいか、を判定します。

マイレシピを見返すと、意味が分かります。

セレクトのポリシーには、usingで、条件がtrue。既存の行は全部見てよい、です。
インサートのポリシーには、with checkで、条件がtrue。どんな行も追加してよい、です。

理屈としては、
インサートには、既存の行が無いので、usingが使えません。
逆に、デリートには、書き込む行が無いので、with checkが使えません。
そういうことです。

### 将来ログインを足したときの姿

usingには、認証されたユーザーのIDと、行のユーザーIDが一致する、と書きます。
自分が作った行だけ見られる、という意味です。

with checkにも、同じ条件を書きます。
自分名義でしか作れない、つまり、他人になりすまして作れない、という意味です。

ここで使う関数は、今ログインしている人のIDを返すものです。

重要な注意です。
with checkを書き忘れると、他人のIDを名乗って行を作れてしまいます。

読めないけど書ける、という、中途半端な穴が開きます。
ログインを足すときは、両方書くのが原則です。

### ポリシーが無い操作はどうなるか

拒否されます。

マイレシピにアップデートのポリシーが無いのは、
編集機能を作らない、という設計を、データベースのレベルでも保証するためでした。

ただし、RLS自体が無効の場合は、話が別です。
その場合は、誰でも何でもできます。

ポリシーが無いイコール拒否、というのは、
RLSが有効なときの話です。
ここは間違えやすいので、注意してください。

確認方法は、Authenticationの、Policiesの画面、
あるいは、Table Editorのテーブル詳細です。
テーブルごとのRLSの有効、無効と、ポリシーの一覧が見られます。

RLSが無効のテーブルには、ダッシュボードに警告が出ます。
警告が出ていたら、意図的なものか、必ず確認してください。

## ダッシュボードの各画面

登録しただけで中を見ていない人向けに、ひと通り回ります。

### Table Editor

データを目で見て、手で直す場所です。Excelのような画面です。

行の追加、編集、削除ができます。
開発中のデータ確認に便利です。

ただし、本番データを直接いじると、
アプリを経由しないので、記録が残りません。

マイレシピの設計書で、
お気に入りの編集機能が無いので、直したければTable Editorから直接編集する、
と書かれているのは、この画面のことです。

### SQL Editor

SQLを直接実行する場所です。14章でテーブルを作ったところですね。

スキーマのSQLを貼って実行したり、
後からのテーブル変更、つまりマイグレーションをしたり、
データの一括確認や修正をしたりします。

ここでの警告です。
デリートやアップデートを、条件なしで実行しないでください。
Table Editorと違って、確認画面がありません。

事故を減らすコツがあります。
実行前に、まずセレクトで対象を確認する癖をつけることです。

まず、その条件でセレクトして、件数が想定どおりかを見る。
想定どおりなら、同じ条件でデリートする。この2段階です。

### Database

データベースの内部設定です。
初心者が見る項目は多くありませんが、
バックアップスと、エクステンションズは、知っておく価値があります。

テーブルズとインデックスィズ。テーブルとインデックスの一覧。
ロールズ。ロールの管理。
エクステンションズ。機能の追加です。位置情報、全文検索、暗号化など。
バックアップス。バックアップです。無料プランでは、提供範囲が限られます。
マイグレーションズ。スキーマ変更の履歴です。

### Authentication

ログイン機能の設定です。
マイレシピでは使いませんが、商用化では必ず使うことになります。

ユーザーズ。登録ユーザーの一覧。
プロバイダーズ。メール、Google、GitHubなどのログイン方法。
イーメール・テンプレーツ。確認メールや、パスワードリセットの文面。
SMTPセッティングス。メールをどこから送るか。商用では必須の設定です。
そして、ポリシーズ。RLSポリシーの一覧です。

### Storage

画像やPDFなどの、ファイル置き場です。

サーバーレスではファイルを保存できないので、
ファイルを扱うなら、ここか、同種のサービスを使います。

こちらにも、バケット単位のポリシーがあります。RLSと同じ考え方です。

### Logs、Reports、Advisors

ログズ。APIへのリクエスト、データベースのクエリ、認証のログが見られます。

レポーツ。データ量、APIリクエスト数、帯域などの使用状況です。

そして、アドバイザーズ。
セキュリティと性能の問題を、自動で指摘してくれます。

アドバイザーズは、必ず一度は見てください。

RLSが無効なテーブルがあります、とか、
このクエリにインデックスがありません、といった指摘が、具体的に出ます。

無料で受けられるレビューです。

### Settings の API

接続に必要な情報の場所です。14章で使いました。

プロジェクトURL。
パブリッシャブルキー、旧anonキー。
そして、シークレットキー、旧サービスロールキー。
これは、表示させたら、すぐ閉じてください。

## 無料プランで知っておくべきこと

5項目あります。

一時停止。
一定期間、およそ1週間アクセスが無いと、自動で停止します。
手動で再開でき、データは消えません。

プロジェクト数。
組織あたりの、同時アクティブ数に上限があります。

容量。
データベース、ストレージ、帯域に上限があります。

バックアップ。
自動バックアップは提供されない、あるいは限定的です。

サポート。
コミュニティのみです。

このうち、実際に困る点が2つあります。

1つめ、一時停止。
しばらく使わないと止まります。再開すればデータは戻りますが、
その間、アプリはエラーになります。
個人利用なら許容できますが、人に使わせるなら、致命的です。

2つめ、バックアップが無いこと。
誤ってデリートを実行したら、戻せません。
25章で扱いますが、商用化の際に、最初に手当てすべき項目です。

### プロジェクト数の上限に達したら

削除ではなく、一時停止で枠を空けることを検討してください。
一時停止ならデータは残り、後から復元できます。削除は、取り返しがつきません。

なお、対象が他プロジェクトの本番データを含む可能性があります。
停止する前に、それが何のプロジェクトか、必ず確認してください。

## スキーマ変更 マイグレーションの考え方

16章で触れた話を、もう少し体系的に扱います。

### 2つの世界を、常に一致させる

1つめが、スキーマのSQLファイル、つまりコード。これから作る環境のためのものです。
2つめが、実際のSupabaseプロジェクト、つまり現物。今動いている環境です。

コードを変えても、現物は勝手に変わりません。必ず両方を更新します。

列を追加するときは、
コードの定義に追記し、現物にはテーブル変更の命令で列を追加します。

列を削除するときは、
コードの定義から削除し、現物にはドロップ・カラムを実行します。
このときデータが消えるので、注意してください。

ポリシーやインデックスの追加は、
コードに追記して、現物には同じSQLを実行します。

### 列を追加するときの鉄則

2つあります。

1つめ。if not exists を付けること。2回実行しても壊れません。

2つめ。not null を付けるなら、デフォルトも必須であること。
既存の行には値が無いので、既定値がないと、エラーになります。

この、何度実行しても同じ結果になる形で書くことを、
冪等、べきとう、と言います。
マイグレーションは、冪等に書くのが基本です。

### より本格的なやり方

プロジェクトが育ってきたら、Supabase CLIを使って、
マイグレーションのファイルをバージョン管理する方式に移行できます。

タイムスタンプ付きのファイル名で、変更を1つずつ記録していく方式です。

変更の履歴が残り、他の環境に同じ変更を順番に適用できるようになります。
チーム開発や商用化では、こちらが標準です。

## パフォーマンスの基本

個人利用では問題になりませんが、知識として、3つ紹介します。

### インデックス

14章で作りました。よく使う検索や並び替えの条件に付けます。

付けすぎると、書き込みが遅くなります。

アドバイザーズが、このクエリにインデックスがありません、と教えてくれるので、
それに従うのが効率的です。

### N+1問題

初心者が最も踏みやすい、性能の罠です。

悪い例は、
お気に入り一覧を1回のクエリで取得したあと、
各件について、追加情報を1件ずつ取得すること。
100件なら100回、合計101回の通信になります。

良い例は、
必要な情報を、1回のクエリでまとめて取得することです。

マイレシピは1テーブルしかないので発生しませんが、
テーブルが増えたら、必ず意識する項目です。

### 接続数

サーバーレス関数は、リクエストのたびに起動します。

アクセスが増えると、その分だけ、データベースへの接続が同時に発生します。

PostgreSQLには、同時接続数の上限があります。
なので、大量アクセス時は、接続プーラー、
つまり接続を使い回す仕組みを経由する構成が必要になります。
Supabaseは、これを標準で提供しています。

なお、PostgREST経由、つまりマイレシピの構成では、
この点はSupabase側が面倒を見てくれています。
意識が必要になるのは、ORMで直接接続する構成にしたときです。

## この章のまとめ

Supabaseは、PostgreSQLに、REST API、Auth、Storage、Realtimeを足した集合体です。

JavaScriptクライアントは、データベースに直接繋がず、
HTTPSでPostgRESTを呼んでいます。

キーは2種類。
パブリッシャブル、旧anonは公開可。
シークレット、旧サービスロールは、絶対に公開不可。

キーは名乗り、権限はRLS。
RLSが無ければ、キーの公開は、全開放を意味します。

RLSのusingは既存の行、with checkは書き込む行。
ログインを足すときは、両方書きます。

アドバイザーズを見れば、セキュリティと性能の問題を教えてもらえます。

無料プランは、一定期間で自動停止し、バックアップが限定的です。

スキーマ変更は、SQLファイルと実際のデータベースの、両方に適用します。
そして、冪等に書きます。

次は、ここまでの構成を、商用に耐える形にするには何が要るか、です。
