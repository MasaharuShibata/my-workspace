# 音声版 23章 Vercel なぜpushしただけで公開されるのか

この章のゴールは、Vercelが何をしているサービスなのかを理解し、
設定画面の各項目が、何のためにあるかを説明できるようになることです。

18章では、手順どおりに登録しました。この章は、その中身です。

## Vercelは何を代行しているサービスなのか

自分でWebアプリを公開しようとすると、本来、これだけの作業が必要です。
10項目あります。

1つめ、サーバーを用意する。クラウドで仮想マシンを借ります。
2つめ、OSとNode.jsを入れる。手作業です。セキュリティ更新も自分でやります。
3つめ、コードを送り込む。転送の仕組みを作ります。
4つめ、インストールとビルドを実行する。自動化スクリプトを書きます。
5つめ、アプリを常時起動させる。プロセス管理を設定します。
6つめ、落ちたら再起動させる。監視の仕組みが要ります。
7つめ、ドメインを繋ぐ。DNS設定です。
8つめ、HTTPS証明書を取得して更新する。90日ごとの自動更新を設定します。
9つめ、世界中から速く見えるようにする。CDNを契約して設定します。
10個め、アクセスが増えたら増強する。負荷分散の設計です。

Vercelは、この10個を全部やります。
あなたがやるのは、git push だけです。

このような、サーバーの存在を意識しなくていい形態を、
サーバーレス、あるいは、PaaS、プラットフォーム・アズ・ア・サービス、と呼びます。

サーバーが無いわけではありません。
あなたが管理しなくていい、という意味です。

## なぜpushすると自動でデプロイされるのか

ここが、一番の疑問だと思います。
魔法ではなく、Webhookという仕組みです。

### 仕組みの全体像

まず、準備段階。これは一度だけです。

あなたが、VercelにGitHubアカウントを連携します。
すると、GitHubに、Vercelという名前のGitHub Appが、リポジトリにインストールされます。
これにより、GitHubは、
このリポジトリに変化があったらVercelに知らせる、という約束を持ちます。

そして以降は、毎回、この流れです。

1つめ、あなたが git push する。
2つめ、GitHubがコードを受け取る。
3つめ、GitHubが、変化がありました、とVercelのURLへ通知を送る。これがWebhookです。
4つめ、Vercelが通知を受け取り、そのリポジトリをコピーする。
5つめ、Vercelが、インストールとビルドを実行する。
6つめ、Vercelが、成果物を世界中のサーバーに配置する。
7つめ、Vercelが、URLを新しいものに切り替える。

### Webhookとは

何かが起きたら、指定のURLに知らせてください、という予約のことです。

通常のAPIは、こちらから、何かあった、と聞きに行きます。これをポーリングと呼びます。
Webhookは、向こうから、ありましたよ、と教えに来ます。

つまり、VercelがGitHubを定期的に見張っているわけでは、ありません。
GitHubが、変化した瞬間にVercelを叩いています。だから数秒で反応します。

### GitHub Appが持っている権限

連携したとき、あなたはGitHub Appに、4つの権限を与えています。

リポジトリの読み取り。コードをコピーしてビルドするためです。
Webhookの受信。プッシュやプルリクエストの検知です。
プルリクエストへのコメント。プレビューURLの自動投稿です。
そして、コミットステータスの書き込み。
GitHub上に、デプロイ成功、あるいは失敗、と表示するためです。

プルリクエストを作ると自動でVercelがコメントを付けるのは、この権限のおかげです。

GitHubとVercelは、あなたが繋いだから会話できているのであって、
最初から繋がっているわけでは、ありません。

連携を確認したり解除したりする場所は、2つあります。
GitHub側は、セッティングスの、インテグレーションズの、アプリケーションズ。
Vercel側は、プロジェクトのセッティングスの、Gitの項目です。

## ビルドの中で何が起きているか

Vercelのダッシュボードで、デプロイのログを開いてみてください。
4つの段階があります。

1つめ、クローニング。GitHubからコードをコピーします。
どのブランチの、どのコミットかが記録されます。

2つめ、インストール。package.jsonを見て、部品をダウンロードします。

3つめ、ビルド。next build を実行します。
TypeScriptの変換、最適化、そして静的ページの生成です。

4つめ、デプロイイング。成果物を配置して、URLを切り替えます。

17章で、npm run build をローカルで試したのは、この段階を先取りするためです。
ローカルで落ちるものは、ここでも必ず落ちます。

### ビルド結果の2種類

ログに出てくる、白丸と、fのような記号の意味が、ここで効いてきます。

白丸は、静的。世界中のCDN、つまりエッジに置かれます。
ビルド時に1回だけ作られます。

fのような記号は、動的。サーバーレス関数として置かれます。
アクセスのたびに実行されます。

利用者がエッジにアクセスすると、
静的ファイル、つまりCSSやJavaScriptや画像や静的ページは、そこで即座に返されます。速いです。
動的ページやAPIは、サーバーレス関数を起動して実行します。

マイレシピでは、
トップページが静的です。
中身はブラウザ側で動くので、HTMLは固定でよいからです。

お気に入りページが動的です。
データベースの中身で変わるので、毎回実行します。force-dynamic の効果ですね。

そして、レシピ生成のAPIも、当然、動的です。

静的にできるものは、静的にするほど、速く、安くなります。

Next.jsが、できるだけ静的にしよう、とするのは、このためです。
15章で force-dynamic を明示的に書いたのは、それを意図的に止めた、ということです。

### サーバーレス関数とは

アクセスが来たときだけ起動して、処理して、終了するプログラムです。

従来のサーバーと比べます。

起動について。従来はずっと動いている。サーバーレスは呼ばれたときだけ。
料金について。従来は動いている時間ぶん。サーバーレスは実行した回数と時間ぶん。
アクセス増加時。従来は自分で増強する。サーバーレスは自動で並列に増える。
初回の遅さ。従来は無い。サーバーレスは起動に少し時間がかかる。
これを、コールドスタートと呼びます。

なお、実行時間には上限があります。プランによります。

AIの呼び出しが長引くと、504、タイムアウトになることがあります。

マイレシピが、ストリーミングを使わない、と設計で決めたのは、
出力が1000トークン程度と短く、この上限に余裕があるからです。

## デプロイの種類 ProductionとPreview

Vercelは、ブランチによって扱いを変えます。

mainブランチ、正確にはProduction Branchに設定されたブランチにプッシュすると、
プロダクション、つまり本番デプロイになります。URLは、本番ドメインです。

それ以外のブランチにプッシュすると、プレビューになります。
URLは、そのブランチ用の一時的なURLです。

だから18章で、ブランチを使った安全な進め方を紹介しました。
本番を壊さずに、本物の環境で確認できます。

Production Branchの設定場所は、セッティングスの、Gitの中です。
既定はmainです。ここを変えると、どのブランチが本番か、が変わります。

この設定を知らないと、
developにプッシュしたのに本番が変わらない、とか、
mainにプッシュしたら本番が変わってしまった、という混乱が起きます。

### デプロイは積み重なる

Vercelは、過去のデプロイを消しません。
1回のデプロイごとに、固有のURLが作られ、そのまま残ります。

本番ドメインは、エイリアス、つまり別名として、
最新のデプロイを指している状態です。
1つ前のデプロイも、その前のデプロイも、固有のURLで、まだ生きています。

この構造のおかげで、ロールバック、つまり切り戻しが、一瞬です。

デプロイメンツの画面から、戻したいデプロイを選んで、
プロモート・トゥ・プロダクション、あるいは、インスタント・ロールバック、を押します。

ビルドし直さず、指し先を変えるだけなので、数秒で戻ります。

そして、18章で、デプロイ固有URLで動作確認するな、と言った理由が、ここで繋がります。

固有URLは、開発者が中身を確認するためのものです。
なので、既定で、Vercelへのログインが必要な保護がかかっています。

本番ドメイン、つまり短いほうには、その保護がかかりません。

## 環境変数の設定 ここが最も詰まる

セッティングスの、エンバイロメント・バリアブルズです。

### 3つの環境スコープ

登録するとき、どの環境で使うかを選びます。

プロダクション。本番デプロイに適用されます。
プレビュー。ブランチのプレビューデプロイに適用されます。
デベロップメント。ローカル開発用です。
通常は .env.local を使うので、不要です。

ここで注意です。
プロダクションにだけ登録すると、プレビュー環境で動きません。

mainでは動くのに、ブランチのプレビューだと500になる、という現象の、典型的な原因です。

個人開発なら、プロダクションとプレビューの両方にチェックを入れておくのが、無難です。

### 変更しても、すぐには反映されない

環境変数を追加、変更したあとは、再デプロイが必要です。
デプロイメンツから、最新のデプロイの、リデプロイを選びます。

理由は2つあります。

AnthropicのAPIキーのような、サーバー専用の変数は、実行時に読まれます。
なので、関数を作り直すために、再デプロイが必要です。

そして、ネクスト・パブリックの接頭辞が付いた変数は、
ビルド時にコードへ埋め込まれます。
なので、必ずビルドし直す必要があります。

ネクスト・パブリックの変数は、ビルド時に、文字列として置換されています。

だから、ビルド済みの成果物を差し替えない限り、古い値のままです。
値を直したのに変わらない、という現象の原因は、これです。

なお、登録済みの値は、既定では伏せ字になっています。
必要なら目のアイコンで表示できますが、
画面共有中は、絶対に押さないでください。

## 主要な設定項目の一覧

セッティングスの配下の項目を、何のためにあるか、で整理します。

### General

フレームワーク・プリセット。どのフレームワークか。ビルド方法が決まります。
マイレシピでは、Next.jsが自動検出されます。

ルート・ディレクトリ。リポジトリのどこにアプリがあるか。
マイレシピでは、リポジトリ直下ではないので、指定が必要です。

ビルドコマンド、出力ディレクトリ、インストールコマンド、Node.jsのバージョン。
これらは、既定のままです。

ルート・ディレクトリは、モノレポで必須です。
モノレポというのは、1つのリポジトリに複数プロジェクトがある構成のことです。

このワークスペースのリポジトリには、マイレシピや家計簿など、複数あります。
なので、これを指定しないと、package.jsonが見つかりません、で失敗します。

### Domains

独自ドメインを繋ぐ場所です。5段階です。

ドメインを取得する。ドメイン業者、またはVercelで購入します。
VercelのDomainsに追加する。
Vercelが指示するDNSレコードを、ドメイン業者側で設定する。
Vercelが所有を確認して、HTTPS証明書を自動取得する。
そして、反映までDNSの伝播時間がかかる。22章の話ですね。

### Deployment Protection

誰がこのデプロイを見られるか、の設定です。3種類あります。

Vercel Authentication。
Vercelアカウントでログインした人だけ閲覧可能です。
プレビューには、既定でオンになっています。

Password Protection。
パスワードを知る人だけ閲覧可能です。プランにより利用の可否が異なります。

Protection Bypass for Automation。
自動テストなどが保護を通り抜けるための、専用トークンです。

マイレシピは、URLを知る人は誰でも操作できる、という制約を受け入れた設計です。
それが嫌なら、ここで本番にも保護をかけます。

利用できる保護の種類はプランによって変わるので、実際の画面で確認してください。

### Functions

サーバーレス関数の設定です。2つあります。

ファンクション・リージョン。サーバー処理をどこで動かすか。
Supabaseと揃えると速くなります。22章の話です。

マックス・デュレーション。実行時間の上限です。超えると504になります。

### Git

プロダクション・ブランチ。どのブランチを本番とするか。

イグノアド・ビルド・ステップ。
特定の変更のとき、ビルドをスキップする条件です。

このイグノアド・ビルド・ステップは、モノレポで効きます。
家計簿だけ変更したときに、マイレシピのビルドを走らせない、といった設定ができます。
無駄なビルド時間、つまり無料枠の消費を、減らせます。

## ログの見方

問題が起きたときに見る場所は、2つです。

### ビルドログ

デプロイメンツから、該当のデプロイをクリックします。

デプロイ自体が失敗したときは、ここです。
npm run build の出力が、そのまま出ます。

よくある失敗が3つ。

モジュールが見つかりません。
インポートのパスの誤りか、大文字小文字の違いです。
ローカルがMacで、VercelがLinuxだからです。

型エラー。TypeScriptの型エラーです。

package.jsonが見つかりません。ルート・ディレクトリの設定漏れです。

### ランタイムログ

プロジェクトの、Logsの画面です。

デプロイは成功したのに動かないときは、ここです。
console.log と console.error の出力が、ここに出ます。

ここで警告です。
ログに秘密情報を出さないでください。

APIキーやデータベースの接続情報をコンソールに出すと、ログに残ります。
デバッグで一時的に出したら、必ず消します。

## 料金プランの考え方

3つのプランがあります。

Hobbyプラン。個人の、非商用プロジェクト向けです。無料です。
Proプラン。個人や小規模チームの商用向けです。ユーザー単位の月額です。
Enterpriseプラン。大規模組織向けで、個別見積もりです。

ここが、商用化で最も重要な点です。

Hobbyプランは、非商用限定です。

広告を載せる、課金する、業務で使う。
こういった場合は、Proプランへの移行が必要です。

マイレシピは個人利用なので、Hobbyで問題ありません。
ですが、もし人に売る、広告を出す、となったら、まずここが変わります。
25章で、再度扱います。

そして、消費される資源が4つあります。
帯域幅。配信したデータ量です。
関数の実行時間。サーバー処理の合計時間です。
ビルド時間。デプロイのたびに消費します。
そして、同時ビルド数。Hobbyは1つずつです。

個人利用で、これらを使い切ることは、まずありません。
気にすべきは、むしろ、Anthropic APIの従量課金のほうです。

## チームが必要な理由

18章で、Vercelでプロジェクトを作るにはチームが必要、と言いました。

Vercelは、プロジェクトの所有単位を、Team、スコープで管理しています。

個人アカウント単体だと、この所有者が定まらず、
プロジェクト作成や、一部の操作ができない場合があります。

チーム作成自体は、無料です。Hobby相当です。
作成時にProプランを勧められますが、選ばなくて構いません。

なお、チームを新しく作った直後は、
外部ツール、たとえばClaudeのコネクタなどが、そのチームを認識しないことがあります。
認可時点の情報がキャッシュされているためです。
接続を切って、繋ぎ直すと、解決します。

## Vercelができないこと

何でもやってくれる、わけではないので、境界を知っておきます。5つあります。

データを永続的に保存すること。
これは、Supabaseなどのデータベースを使います。

ファイルを保存すること。
Vercel Blob、Supabase Storage、S3などを使います。

長時間動き続ける処理。
別のサービス、ジョブ実行基盤へ回します。

環境変数をAPI経由で登録すること。
これはダッシュボードから手作業です。
自動化ツールからは登録できない場合があります。

そして、メールを送ること。
専用サービスが必要です。25章で扱います。

ここで一番大きな違いを言います。
サーバーレス関数は、処理が終わると消えます。

ファイルを書き出しても、次のリクエストでは存在しません。
サーバーに保存する、という発想が通用しないのが、最も大きな違いです。

## この章のまとめ

Vercelは、サーバー調達からHTTPS、CDNまでを代行するサービスです。

プッシュで自動デプロイされるのは、Webhookのおかげです。
GitHub Appを入れたから、GitHubがVercelに通知しています。

ビルドの結果は、静的なエッジ配信と、動的なサーバーレス関数に分かれます。

mainブランチはプロダクション、他のブランチはプレビューです。

デプロイは積み重なるので、ロールバックが一瞬です。

環境変数は、プロダクションとプレビューの両方に登録し、変更後は再デプロイします。

ネクスト・パブリックの変数は、ビルド時に埋め込まれるので、必ずビルドし直します。

ルート・ディレクトリは、モノレポで必須です。

問題が起きたら、デプロイ失敗ならビルドログ、実行時ならランタイムログ。

Hobbyプランは非商用限定です。商用ならProへ。

サーバーレス関数に、ファイルを保存しても消えます。
