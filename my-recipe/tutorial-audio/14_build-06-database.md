# 音声版 14章 ステップ6 データベースに保存する

この章のゴールは、Supabaseにテーブルを作り、
お気に入り登録ボタンで、レシピが1件保存されるようにすることです。

この章で新しく学ぶことは4つです。
SQL、つまりテーブルを作る命令。
RLS、データベース側のアクセス制御。
Supabaseクライアント、JavaScriptからデータベースを読み書きする道具。
そしてサーバーアクション。7章で学んだ、サーバー側の関数です。

## Supabaseのプロジェクトを作る

手順は3つです。

1つめ。Supabaseのサイトに、GitHubアカウントでログインします。
2つめ。ニュー・プロジェクト、で新規プロジェクトを作成します。
プロジェクト名は任意。
リージョンは、ノースイースト・アジア、東京を推奨します。近いほうが速いからです。
データベースのパスワードは、自動生成で構いません。今回は直接使いません。
3つめ。作成完了まで、1分から2分待ちます。

ここでひとつ注意があります。
無料プランには、アクティブなプロジェクト数の上限があります。
組織あたり2件、といった制限です。

上限に達したら、使っていないプロジェクトを、
削除ではなく、一時停止、ポーズしてください。
一時停止なら、データは消えず、後から復元できます。

## SQLでテーブルを作る

SQLとは、データベースに命令するための言語です。
今回使うのは、実質これだけです。

create table、表を作る。
insert、行を追加する。
select、行を読む。
delete、行を消す。
alter table、表の定義を変える。

このうち、インサート、セレクト、デリートは、
SupabaseのJavaScriptライブラリ経由で書きます。
なので、直接SQLで書くのは、create table だけです。

### スキーマのSQLを書く

supabaseフォルダの中に、schema、というSQLファイルを作ります。
設計書、詳細設計書の5節で決めた列定義を、そのままSQLにします。

テーブル名は、favorite_recipes。
列は、ID、タイトル、ジャンル、調理時間、人数、
元になった食材、材料、手順、そして作成日時の9つです。

1行ずつ、指定の意味を説明します。

create table if not exists、と書きます。
これは、無ければ作る、既にあれば何もしない、という意味です。
再実行しても壊れません。

IDには、uuid型を指定し、primary key、主キーと宣言します。
主キーというのは、1行を一意に特定するための列です。
そして、デフォルトとして、ランダムなIDを自動生成する関数を指定します。

文字列の列には、text型を指定し、not null、つまり空を許さない、と宣言します。
ジャンルには、デフォルトとして、こだわりなし、を指定します。
指定しなかったときの既定値です。

作成日時には、timestamptz、タイムスタンプ・ウィズ・タイムゾーン型を指定し、
デフォルトとして、現在時刻を返す関数を指定します。
登録した瞬間の時刻が、自動で入ります。

そして最後に、create index で、作成日時の降順のインデックスを作ります。

### uuidを使う理由

IDを、1、2、3、という連番にすることもできます。
ですが、UUID、つまり長いランダム文字列を使っています。理由があります。

連番だと、URLに、スラッシュ、レシピズ、スラッシュ、5、と出たとき、
6を試せば、他人のデータが見られてしまいます。
UUIDなら、推測できません。

今回は個人利用なので影響は小さいですが、
癖として安全なほうを選んでおく価値があります。

### インデックスとは

本の索引と同じです。

作成日時の降順で並べることが多い、と分かっているので、
あらかじめ、並んだ状態のメモを作らせておきます。
データが増えたときの、表示速度が変わります。

ただし、インデックスは万能ではありません。
作るほど、書き込みは遅くなります。
よく使う検索や並び替えにだけ付けるものです。

## RLS データベース側のアクセス制御

SQLファイルの続きに、RLSの設定を書きます。

まず、テーブルに対して、enable row level security、と書いて、RLSを有効にします。
そして、ポリシーを3つ作ります。
セレクト用、インサート用、デリート用です。

RLS、ロウ・レベル・セキュリティとは、
どの行を、誰が、どう操作できるかを、
データベース自身に守らせる仕組みです。

重要なのは、アプリのコードがどうであれ、データベースが拒否する、という点です。
アプリにバグがあっても、データベースが最後の砦になります。

今回のポリシーは、3つとも、条件がtrue、つまり常に許可です。
誰でも全部できる設定です。

### なぜ、わざわざ全部許可を書くのか

RLSを無効のままにしても、同じように動きます。
では、なぜ有効にして、常に許可、というポリシーを書くのか。

基本設計書の5.1節の説明が、秀逸です。

無効化ではなく、意図的に開放したポリシーにすることで、
将来ログインを追加する場合に、
ポリシーの条件式を差し替えるだけで済むようにしている、と。

将来ログインを足すとき、
今は、条件がtrue、と書いてあるところを、
認証されたユーザーのIDと、行のユーザーIDが一致する、という条件に変えるだけです。

もしRLSが無効だと、有効化と、ポリシーの作成と、全体の動作確認が必要になります。
今の手間はほぼ同じで、将来の手間が減る。
これが、良い設計判断の形です。

もうひとつの効果があります。
開放されている、ということが、SQLに明示されることです。

後から見た人が、
セキュリティ設定を忘れているのか、意図的に開けているのかを、判断できます。

### アップデートのポリシーが無い理由

編集機能を作らないからです。要件定義のスコープ外ですね。

そして、ポリシーが無い操作は、拒否されます。
つまり、編集機能を作らない、ということが、
データベースのレベルでも保証されている状態です。

## SQLを実行する

手順は4つです。

Supabaseの左メニューから、SQL Editorを開きます。
ニュー・クエリを選びます。
作ったSQLファイルの中身を、全部コピーして貼り付けます。
そして、Run、実行を押します。

サクセス、ノー・ロウズ・リターンド、と出れば成功です。

左メニューのTable Editorで、テーブルが0件の状態でできていることを確認します。

## 接続情報を取得する

左メニューのプロジェクト設定、歯車のアイコンから、APIの画面を開きます。
そして、2つの値を控えます。

1つめが、プロジェクトURL。
2つめが、パブリッシャブルキー、あるいはanonキーです。

ここで、絶対に守ってほしいことがあります。
service_role key、サービスロールキーは、絶対に使わないでください。

これは、RLSをすべて無視できる、管理者用の鍵です。
ブラウザに渡ったら、終わりです。
今回のアプリでは、使う場面がありません。

取得した2つの値を、.env.local に追記します。
どちらも、ネクスト・アンダーバー・パブリック、の接頭辞を付けます。

### なぜSupabaseのキーには、公開の接頭辞を付けるのか

7章で、秘密のものには付けない、と学びました。
矛盾しているようですが、違います。

Anthropicのキーは、これ単体でお金が使えます。だから絶対に秘密です。

一方、Supabaseのanonキーは、公開される前提で設計されています。
何ができるかは、RLSが決めます。

anonキーは、あなたはログインしていない人ですね、と名乗るための札であって、
権限そのものではありません。
実際に何ができるかは、RLSのポリシーが決めるのです。

ただし今回は、RLSが全部許可です。
なので、結果として、キーを知る人は誰でも読み書きできます。

これは、要件定義の3.3節で明記されている、承知のうえの制約です。
気になる場合は、Vercelのパスワード保護をかけます。

## Supabaseクライアントを作る

まず、Supabaseの公式ライブラリをインストールします。

そして、libフォルダの中のsupabaseフォルダに、server、というファイルを作ります。

中身は、createClient、という関数をエクスポートするだけです。
その中で、環境変数のURLとanonキーを渡して、Supabaseのクライアントを作ります。

ここで2つ、説明すべきことがあります。

### 末尾のビックリマークは何か

環境変数の値の型は、文字列またはundefined、です。
環境変数が設定されていない可能性があるからです。

末尾に付けるビックリマークは、非nullアサーションといって、
これは必ずある、と保証する宣言です。

asと同じく、これはTypeScriptを黙らせるだけです。
環境変数が未設定なら、実行時にエラーになります。

ただし、設定されていなければ、どのみち動きません。
なので、ここはビックリマークを使うのが、実用的な判断です。

### なぜクライアント作成を関数にしているのか

変数に入れて使い回すこともできますが、
関数にしておくと、呼ばれるたびに新しいクライアントを作る形になります。

サーバー側では、複数のリクエストが同時に走ります。
なので、1つのインスタンスを使い回して、状態が混ざる、という事故を避けられます。

また、将来ログインを追加して、リクエストごとにcookieを読む形になっても、
呼び出し側を変えずに済みます。

## サーバーアクションを書く

appフォルダの直下に、actions、というファイルを作ります。
先頭に、use server、と書きます。

このファイルの関数はすべてサーバーで実行される、という宣言です。
クライアントコンポーネントから普通にインポートして呼べますが、
中身のコードはブラウザに送られません。

中に、addFavorite、という関数を作ります。
引数は、レシピ、元になった食材の文字列、そしてジャンルです。

中では、Supabaseのクライアントを作って、
favorite_recipes テーブルに対して、インサートを実行します。

読み下すと、このテーブルに、このオブジェクトを1行追加する、です。
SQLのインサート文を、JavaScriptで書いているだけです。

結果からは、分割代入でエラーだけを取り出します。

### ここがステップ6の核心 配列から文字列への変換

材料と手順を渡すところで、ジョインをかけています。
区切り文字は、バックスラッシュとnで表される、改行の文字です。

5章の演習で扱った、あの境界です。

画面とAIの側では、材料は文字列の配列です。
データベースの側では、材料は、改行区切りの1つの文字列です。

保存するときは、ジョインで、配列から、改行区切りの文字列へ。
表示するときは、スプリットで、文字列から、配列へ。これはステップ7で使います。

この設計は、材料を個別に検索しない、という要件だからこそ成立しています。
設計判断が、コードのこの1行に現れている、という良い例です。

### 列名がスネークケースになっている

調理時間を渡すところでは、
左側がデータベースの列名、アンダーバー区切り。
右側がJavaScriptのプロパティ名、キャメルケースになっています。

9章で型定義を分けた理由が、ここで効いてきます。

なお、ジャンルのところは、キー名と変数名が同じなので、
片方だけ書く省略記法を使っています。

### エラー処理

ここは重要です。
Supabaseのライブラリは、例外を投げません。

データとエラー、という形で結果を返してくるので、
エラーを自分で確認する必要があります。

ここを忘れると、失敗しているのに、登録しました、と表示されます。
エラーが返っていないか確認する。これは必ずやってください。

エラーがあれば、お気に入りの登録に失敗しました、
時間をおいて再度お試しください、というメッセージを返します。

### revalidatePath

最後に、リバリデート・パスで、
お気に入り一覧ページのキャッシュを捨てて、と指示します。

これがあるので、登録直後に一覧ページを開くと、最新の状態が表示されます。

## 画面から呼ぶ

レシピ結果の部品に、保存処理を足します。
stateを使うので、先頭に use client を追加します。

stateは3つ必要です。

saving、保存中かどうか。ボタンを無効にして、二重登録を防ぎます。
saved、保存済みかどうか。同じレシピを何度も登録させないためです。
そしてerror、失敗メッセージです。

保存の処理では、
保存中フラグを立てて、エラーを消して、サーバーアクションを呼びます。
返ってきたら、保存中フラグを下ろします。
エラーがあれば、それを表示して、早期リターン。
なければ、保存済みフラグを立てます。

ボタンのdisabled属性には、保存中、または、保存済み、を指定します。
縦棒2つが、または、という意味です。

ボタンの文字は、三項演算子のネストで切り替えます。
保存済みなら、お気に入りに登録しました。
そうでなくて保存中なら、登録中。
どちらでもなければ、お気に入り登録、です。

三項演算子のネストは、2段までが限界です。
3段以上になったら、早期リターンや、関数に切り出してください。

### サーバー側の関数を、なぜ普通に呼べるのか

use client のファイルから、use server の関数をインポートして呼んでいます。

実際には、ブラウザからサーバーへの通信が発生していますが、Next.jsが隠しています。
フェッチも、ストリンギファイも書かなくていい。
これがサーバーアクションの利点です。

## 動作確認

手順は4つです。

レシピを生成する。
お気に入り登録を押す。
ボタンが、登録中、から、お気に入りに登録しました、に変わる。
そして、SupabaseのTable Editorを開いて、1行増えていることを確認する。

Table Editorで見るべきところは4つです。

IDに、UUIDが自動で入っていること。
材料が、改行区切りで複数行になっていること。
ジャンルに、選んだジャンルが入っていること。
作成日時に、現在時刻が自動で入っていること。

材料のセルをクリックすると、中身が複数行で見えます。
ジョインが効いている証拠です。

### わざと失敗させてみる

.env.local のSupabaseのanonキーを、1文字変えて再起動し、
登録を試してみてください。
エラーメッセージが表示されるはずです。

エラー処理は、わざと失敗させないと確認できません。

成功したから大丈夫、ではなく、失敗したときの挙動も試す。
この癖をつけてください。

確認できたら、キーは元に戻します。
