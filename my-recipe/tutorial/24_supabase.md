# 24. Supabase — データベースは何をしてくれているのか

> この章のゴール: Supabaseが何の集合体なのかを理解し、
> キーの種類・RLS・ダッシュボードの各画面の意味を説明できるようになる。

---

## 24.1 Supabaseは「PostgreSQL + 周辺装備」

Supabaseの正体は **PostgreSQL(ポストグレス)というデータベース** です。
それに、Webアプリで必要になる装備を足して、ブラウザから使える形にしたものです。

```
┌─────────────────────────────────────────────┐
│ Supabase プロジェクト                        │
│                                             │
│  ┌───────────────────────────────────────┐  │
│  │  PostgreSQL(本体)                    │  │
│  │  ・テーブル、行、列                    │  │
│  │  ・RLS(行レベルの権限)                │  │
│  └───────────────────────────────────────┘  │
│        ▲         ▲         ▲        ▲       │
│   ┌────┴───┐ ┌───┴───┐ ┌───┴───┐ ┌──┴────┐  │
│   │ REST   │ │ Auth  │ │Storage│ │Realtime│ │
│   │ API    │ │(ログイン)│ │(ファイル)│ │(即時反映)│
│   └────────┘ └───────┘ └───────┘ └───────┘  │
└─────────────────────────────────────────────┘
```

| 装備 | 何をするか | my-recipeで使うか |
|---|---|---|
| **PostgreSQL** | データの保管 | **使う** |
| **REST API(PostgREST)** | テーブルをHTTPで読み書きできるようにする | **使う** |
| **Auth** | ログイン・ユーザー管理 | 使わない(意図的に。要件定義 3.3) |
| **Storage** | 画像などファイルの保管 | 使わない |
| **Realtime** | データの変化を即座に画面へ通知 | 使わない |
| **Edge Functions** | サーバー処理(Vercelと同じ役割) | 使わない(Next.js側でやる) |

💡 **「使わない」を明示できているのが、設計をした証拠です。**
Supabaseは多機能なので、全部使おうとすると複雑になります。
必要なものだけ使う、という判断が大事です。

## 24.2 ⚠️ 実はデータベースに直接繋いでいない

ここは多くの人が誤解しています。

```ts
const supabase = createSupabaseClient(url, anonKey);
await supabase.from("favorite_recipes").select("*");
```

このコードは、**データベースに直接接続していません**。
実際に起きているのは、**普通のHTTPSリクエスト** です。

```
あなたのコード
  supabase.from("favorite_recipes").select("*")
        │
        │ 内部で、こういうHTTPリクエストに変換される
        ▼
  GET https://xxxxx.supabase.co/rest/v1/favorite_recipes?select=*
  Headers:
    apikey: sb_publishable_xxxxx
    Authorization: Bearer sb_publishable_xxxxx
        │
        ▼
  Supabase側の PostgREST が受け取る
        │
        │ SQLに変換して実行
        ▼
  SELECT * FROM favorite_recipes;
```

**PostgREST** というソフトが、テーブルを自動的にWeb API化しています。
テーブルを作った瞬間に、そのテーブルのAPIができあがる。これがSupabaseの核心です。

### なぜこれを知っておく必要があるか

| 分かること | 理由 |
|---|---|
| **ブラウザから直接DBを呼べる理由** | HTTPSだから。DBの生プロトコルはブラウザから話せない |
| **anonキーが公開されてよい理由** | キーは「誰として話すか」の宣言にすぎず、**権限はRLSが決める** |
| **F12のNetworkタブに出る理由** | ただのHTTP通信だから |
| **502や504が出ることがある理由** | 間にWebサーバーがいるから |

⚠️ 将来 Prisma などのORMを使うときは、**PostgRESTを経由せず
データベースに直接接続する** 別の経路を使います。そのときは接続文字列
(`postgresql://...`)が必要になり、**扱いがまったく変わります**
(こちらは絶対に公開できません)。

## 24.3 キーの種類 — 一番大事な話

Supabaseのキーは **2種類** あります。名称が新旧で違うので、両方覚えてください。

| 新しい名称 | 旧称 | 性質 | 置き場所 |
|---|---|---|---|
| **Publishable key**(`sb_publishable_...`) | anon key / public key | **公開してよい** | ブラウザでもOK |
| **Secret key**(`sb_secret_...`) | service_role key | ⚠️ **RLSを全部無視できる** | **サーバーのみ。絶対に公開しない** |

### なぜ publishable(anon)キーは公開してよいのか

このキーが意味するのは、**「私はログインしていない人です」という名乗り** だけです。
権限は一切含まれていません。

```
キー   = 「私は anon という役割です」
RLS   = 「anon という役割の人は、何をしてよいか」 ← 権限はこっち
```

**RLSが正しく設定されていれば、キーが漏れても被害は限定されます。**
逆に言えば、**RLSを無効にしたままキーを公開したら、全データが読み書きし放題** です。

⚠️ my-recipe は「RLSは有効だが、全部許可」という設定です(14章)。
つまり **キーを知る人は誰でもお気に入りを読み書きできます**。
これは要件定義 3.3 で承知のうえで受け入れた制約でした。

### ⚠️ secret(service_role)キーは何が危険なのか

**RLSを完全に無視します。** どんなポリシーが設定されていても、全テーブルを
読み書き・削除できます。管理者の合鍵です。

| 絶対にやってはいけないこと |
|---|
| ブラウザ側のコードに書く |
| `NEXT_PUBLIC_` を付ける |
| GitHubにコミットする |
| ログに出力する |
| 他人に見せる(画面共有含む) |

💡 my-recipe は **service_role キーを一切使いません**。
使わなければ、漏らす心配もありません。
**必要ないものは取得しない・使わない**、これも立派な安全対策です。

### キーが漏れたときの対処

**Settings → API Keys からキーを再生成(rotate)します。**
古いキーは即座に無効になるので、環境変数の更新を忘れずに。

⚠️ 「漏れたかもしれない」と思った時点で、**迷わず再生成** してください。
様子を見る理由がありません。

## 24.4 RLS(行レベルセキュリティ)を、もう一段深く

14章では「常に許可」のポリシーだけ書きました。仕組みを理解しておきます。

### ロール(役割)

Supabaseにアクセスするとき、あなたは必ず何かの役割を名乗っています。

| ロール | 誰か |
|---|---|
| `anon` | ログインしていない人 |
| `authenticated` | ログイン済みの人 |
| `service_role` | 管理者(RLSを無視) |

### ポリシーの構造

```sql
create policy "ポリシー名"
  on テーブル名
  for 操作種別          -- select / insert / update / delete / all
  to ロール             -- 省略すると全ロール
  using (条件)          -- 既存の行を「見てよいか」
  with check (条件);    -- 新しい行を「作ってよいか」
```

### ⚠️ `using` と `with check` の違い

ここは必ず混乱するところなので、表で整理します。

| 句 | いつ評価されるか | 対象 |
|---|---|---|
| `using` | SELECT / UPDATE / DELETE | **既にある行** を見てよいか |
| `with check` | INSERT / UPDATE | **これから書き込む行** が条件を満たすか |

my-recipe を見返すと、意味が分かります。

```sql
create policy "anyone can view favorites"
  on favorite_recipes for select
  using (true);                      -- 既存の行は全部見てよい

create policy "anyone can add favorites"
  on favorite_recipes for insert
  with check (true);                 -- どんな行も追加してよい
```

INSERTには「既存の行」が無いので `using` が使えない。
逆にDELETEには「書き込む行」が無いので `with check` が使えない。
**そういう理屈です。**

### 将来ログインを足したときの姿

```sql
-- 自分が作った行だけ見られる
using (auth.uid() = user_id)

-- 自分名義でしか作れない(他人になりすまして作れない)
with check (auth.uid() = user_id)
```

`auth.uid()` は「今ログインしている人のID」を返す関数です。

⚠️ **`with check` を書き忘れると、他人のIDを名乗って行を作れてしまいます。**
「読めないけど書ける」という中途半端な穴が開きます。
ログインを足すときは、**両方書く** のが原則です。

### ポリシーが無い操作はどうなるか

**拒否されます。** my-recipe に UPDATE のポリシーが無いのは、
「編集機能を作らない」という設計をDBレベルでも保証するためでした(14章)。

⚠️ ただし、RLS自体が **無効** の場合は話が別で、
その場合は誰でも何でもできます。「ポリシーが無い=拒否」は
**RLSが有効なときの話** です。ここは間違えやすいので注意してください。

### 確認方法

**Authentication → Policies**(または Table Editor のテーブル詳細)で、
テーブルごとのRLS有効/無効とポリシー一覧が見られます。

⚠️ **RLSが無効のテーブルには、ダッシュボードに警告が出ます。**
警告が出ていたら、意図的なものか必ず確認してください。

## 24.5 ダッシュボードの各画面

登録しただけで中を見ていない人向けに、ひと通り回ります。

### Table Editor

**データを目で見て、手で直す場所です。** Excelのような画面です。

- 行の追加・編集・削除ができる
- 開発中のデータ確認に便利
- ⚠️ **本番データを直接いじると、アプリを経由しないので記録が残りません**

💡 my-recipe で「お気に入りの編集機能が無いので、直したければ
Table Editor から直接編集する」と設計書に書かれているのは、この画面のことです。

### SQL Editor

**SQLを直接実行する場所です。** 14章でテーブルを作ったところ。

- `schema.sql` を貼って実行
- 後からの `ALTER TABLE`(16章のマイグレーション)
- データの一括確認・修正

⚠️ **`delete` や `update` を条件なしで実行しないでください。**
Table Editor と違って確認画面がありません。

💡 実行前に、まず `select` で対象を確認する癖をつけると事故が減ります。

```sql
-- ① まず対象を確認
select * from favorite_recipes where genre = '中華';
-- ② 件数が想定通りなら、消す
delete from favorite_recipes where genre = '中華';
```

### Database

データベースの内部設定です。初心者が見る項目は多くありませんが、
**Backups** と **Extensions** は知っておく価値があります。

| 項目 | 内容 |
|---|---|
| **Tables / Indexes** | テーブルとインデックスの一覧 |
| **Roles** | ロール(`anon`, `authenticated` など)の管理 |
| **Extensions** | 機能の追加(位置情報、全文検索、暗号化など) |
| **Backups** | ⚠️ **バックアップ。無料プランでは提供範囲が限られる** |
| **Migrations** | スキーマ変更の履歴 |

### Authentication

ログイン機能の設定です。my-recipeでは使いませんが、
**商用化では必ず使うことになります**(25章)。

| 項目 | 内容 |
|---|---|
| Users | 登録ユーザーの一覧 |
| Providers | メール、Google、GitHubなどのログイン方法 |
| **Email Templates** | 確認メール・パスワードリセットの文面 |
| **SMTP Settings** | ⚠️ **メールをどこから送るか。商用では必須設定**(25章) |
| Policies | RLSポリシーの一覧 |

### Storage

画像やPDFなどのファイル置き場です。
**サーバーレスではファイルを保存できない**(23章)ので、
ファイルを扱うならここか、同種のサービスを使います。

こちらにも **バケット単位のポリシー(RLSと同じ考え方)** があります。

### Logs / Reports / Advisors

| 画面 | 内容 |
|---|---|
| **Logs** | APIへのリクエスト、DBのクエリ、認証のログ |
| **Reports** | データ量、APIリクエスト数、帯域などの使用状況 |
| **Advisors** | ⚠️ **セキュリティ・性能の問題を自動で指摘してくれる** |

💡 **Advisors は必ず一度見てください。**
「RLSが無効なテーブルがあります」「このクエリにインデックスがありません」
といった指摘が、具体的に出ます。**無料で受けられるレビュー** です。

### Settings → API

接続に必要な情報の場所です(14章で使いました)。

- Project URL
- Publishable key(旧 anon key)
- Secret key(旧 service_role key)← ⚠️ 表示させたら閉じる

## 24.6 無料プランで知っておくべきこと

| 項目 | 無料プランでの扱い |
|---|---|
| **一時停止** | ⚠️ **一定期間(約1週間)アクセスが無いと自動で停止**。手動で再開でき、データは消えない |
| **プロジェクト数** | 組織あたりの同時アクティブ数に上限あり |
| **容量** | データベース・ストレージ・帯域に上限 |
| **バックアップ** | ⚠️ **自動バックアップは提供されない、または限定的** |
| **サポート** | コミュニティのみ |

⚠️ **2つ、実際に困る点があります。**

**① 一時停止**
しばらく使わないと止まります。再開すればデータは戻りますが、
**その間アプリはエラーになります**。個人利用なら許容できますが、
人に使わせるなら致命的です。

**② バックアップが無い**
誤って `delete` を実行したら、**戻せません**。
25章で扱いますが、商用化の際に最初に手当てすべき項目です。

### プロジェクト数の上限に達したら

**削除ではなく「一時停止(Pause)」で枠を空けることを検討してください。**
一時停止ならデータは残り、後から復元できます。削除は取り返しがつきません。

⚠️ 対象が他プロジェクトの本番データを含む可能性があるので、
**停止する前に、それが何のプロジェクトか必ず確認** してください。

## 24.7 スキーマ変更(マイグレーション)の考え方

16章で触れた話を、もう少し体系的に。

### 2つの世界を、常に一致させる

```
① supabase/schema.sql(コード)     ← これから作る環境のため
② 実際のSupabaseプロジェクト(現物)  ← 今動いている環境
```

⚠️ **①を変えても、②は勝手に変わりません。** 必ず両方を更新します。

| 変更の種類 | ①への操作 | ②への操作 |
|---|---|---|
| 列を追加 | `create table` の定義に追記 | `alter table ... add column if not exists ...` |
| 列を削除 | 定義から削除 | `alter table ... drop column ...`(⚠️ **データが消える**) |
| ポリシー追加 | `create policy` を追記 | 同じSQLを実行 |
| インデックス追加 | `create index` を追記 | 同じSQLを実行 |

### 列を追加するときの鉄則

```sql
alter table favorite_recipes
  add column if not exists genre text not null default 'こだわりなし';
```

- `if not exists` … 2回実行しても壊れない
- `not null` を付けるなら **`default` も必須** …
  既存の行には値が無いので、既定値がないとエラーになる

💡 **「何度実行しても同じ結果になる」形で書く** ことを **冪等(べきとう)** と言います。
マイグレーションは冪等に書くのが基本です。

### より本格的なやり方

プロジェクトが育ってきたら、Supabase CLI を使って
マイグレーションファイルをバージョン管理する方式に移行できます。

```
supabase/migrations/
  20260918120000_create_favorite_recipes.sql
  20260918140000_add_genre_column.sql
```

**変更の履歴が残り、他の環境に同じ変更を順番に適用できる** ようになります。
チーム開発や商用化では、こちらが標準です。

## 24.8 パフォーマンスの基本

個人利用では問題になりませんが、知識として。

### インデックス

14章で作りました。「よく使う検索・並び替えの条件」に付けます。

```sql
create index ... on favorite_recipes (created_at desc);
```

⚠️ 付けすぎると書き込みが遅くなります。**Advisors が「このクエリに
インデックスがありません」と教えてくれる** ので、それに従うのが効率的です。

### N+1問題

初心者が最も踏みやすい性能の罠です。

```
✕ 悪い例
  お気に入り一覧を取得(1回)
  → 各件について、追加情報を1件ずつ取得(100件なら100回)
  → 合計101回の通信

○ 良い例
  必要な情報を1回のクエリでまとめて取得
```

my-recipe は1テーブルしかないので発生しませんが、
**テーブルが増えたら必ず意識する** 項目です。

### 接続数

サーバーレス関数は **リクエストのたびに起動** します(23章)。
アクセスが増えると、その分だけDBへの接続が同時に発生します。

PostgreSQLには同時接続数の上限があるので、大量アクセス時は
**接続プーラー**(接続を使い回す仕組み)を経由する構成が必要になります。
Supabaseはこれを標準で提供しています。

💡 PostgREST経由(my-recipeの構成)では、この点はSupabase側が面倒を見ています。
意識が必要になるのは、ORMで直接接続する構成にしたときです。

## 24.9 この章のまとめ

- Supabaseは **PostgreSQL + REST API + Auth + Storage + Realtime** の集合体
- ⚠️ JSクライアントは **DBに直接繋がず、HTTPSでPostgRESTを呼んでいる**
- キーは2種類。**publishable(anon)は公開可、secret(service_role)は絶対不可**
- **キーは名乗り、権限はRLS**。RLSが無ければキー公開=全開放
- RLSの `using` は **既存の行**、`with check` は **書き込む行**。
  ログインを足すときは **両方書く**
- **Advisors** を見れば、セキュリティと性能の問題を教えてもらえる
- ⚠️ 無料プランは **一定期間で自動停止**、**バックアップが限定的**
- スキーマ変更は **`schema.sql` と実際のDBの両方** に適用する。**冪等に書く**
