# 01. Webアプリとは何か

> この章のゴール: 「ブラウザ」「サーバー」「データベース」「API」が、
> それぞれ何をする係なのかを、人に説明できるようになる。

コードは1行も書きません。ここを飛ばすと、後半で必ず迷子になります。

---

## 1.1 まず、Webサイトを開くと何が起きているのか

ブラウザのアドレス欄に `https://example.com` と打って Enter を押す。
このとき、あなたのパソコンの中では何も起きていません。
起きているのは **世界のどこかにある別のコンピューター** との会話です。

```
あなたのブラウザ                        どこかのコンピューター(サーバー)
     |                                          |
     |  「example.com のトップページください」    |
     |  ─────────────────────────────────────>  |
     |                                          |  (探す・作る)
     |  「はい、これです」(HTMLという文書)       |
     |  <─────────────────────────────────────  |
     |                                          |
   画面に描く
```

この往復のことを **リクエスト(お願い)** と **レスポンス(返事)** と呼びます。
Webアプリの話は、突き詰めると全部これです。誰が誰に何をお願いして、何を返すか。

### 用語: クライアントとサーバー

- **クライアント** = お願いする側。ここではあなたのブラウザ
- **サーバー** = 返事する側。24時間動きっぱなしのコンピューター

「サーバー」は特別な機械ではありません。**返事する役をやっているコンピューター**のことです。
自分のノートPCでも、その役をやらせればサーバーです(実際、開発中はそうします)。

💡 「フロントエンド」はクライアント側で動くもの、「バックエンド」はサーバー側で動くもの、
という呼び分けもよく使われます。同じことを別の角度から呼んでいるだけです。

---

## 1.2 「Webサイト」と「Webアプリ」の違い

| | Webサイト | Webアプリ |
|---|---|---|
| 例 | 会社の紹介ページ、ブログ | Gmail、家計簿、今回のmy-recipe |
| 中身 | 誰が見ても同じ内容 | 操作すると内容が変わる |
| データ | 基本なし | 保存する(データベースが要る) |

境目は曖昧ですが、**「利用者の操作でデータが変わるか」** が実務上の分かれ目です。

my-recipe は、
- 食材を入力する(利用者の入力)
- AIがレシピを返す(その場で作られる、毎回違う内容)
- 気に入ったら保存する(データが残る)

なので、しっかりWebアプリです。

## 1.3 my-recipe に登場する4人の登場人物

このアプリには4つの「場所」が出てきます。ここを混同すると、後で
「APIキーをどこに置くか」で必ず事故ります。

```
┌─────────────────┐
│ ① ブラウザ       │  利用者のスマホ/PCの中。画面と操作を担当
│   (クライアント)  │
└────────┬────────┘
         │ HTTPS
┌────────▼────────┐
│ ② Vercel         │  Next.jsアプリが動いているサーバー。
│   (サーバー)      │  画面を返す + 秘密の処理をする
└───┬─────────┬───┘
    │         │
┌───▼───┐ ┌───▼──────────┐
│ ③ Supabase │ │ ④ Claude API │
│ (データベース)│ │  (AI)        │
└───────────┘ └──────────────┘
```

| # | 名前 | 役割 | 覚え方 |
|---|---|---|---|
| ① | ブラウザ | 画面を表示し、クリックや入力を受け取る | お客さんの手元 |
| ② | Vercel(Next.js) | 画面を組み立てて返す。秘密情報を使う処理をする | お店のカウンターと厨房 |
| ③ | Supabase | お気に入りレシピを保存しておく | 倉庫 |
| ④ | Claude API | 食材からレシピを考える | 外注先の料理人 |

### なぜ ④ を ① から直接呼ばないのか(超重要)

ブラウザから直接 Claude API を呼べば、②を経由せずに済んで一見シンプルです。
**が、絶対にやってはいけません。**

Claude API を使うには **APIキー** という「お金を払う権利の証明書」が要ります。
ブラウザで動くコードは、**利用者が全部中身を見られます**(F12を押せば誰でも読めます)。
つまりブラウザにAPIキーを置いた瞬間、世界中の誰でもあなたのお金でAIを使えるようになります。

```
✕ 危険な構成
ブラウザ ──(APIキーを持って)──> Claude API
          ↑ここが丸見え

○ 正しい構成
ブラウザ ──(食材だけ送る)──> Vercel ──(APIキーを持って)──> Claude API
                              ↑ここはブラウザから見えない
```

これが設計書(`docs/01_requirements.md` 3.3節)に書かれている
「APIキーはブラウザに一切公開せず、サーバー側からのみ呼び出す」の意味です。

⚠️ この教材で後ほど `NEXT_PUBLIC_` という接頭辞が出てきます。
これが **付いている変数はブラウザに公開される**、**付いていないものはサーバーだけ**、
というルールです。APIキーに付けたら即アウトです。

## 1.4 データベースとは何か

「表計算ソフトを、プログラムから安全に読み書きできるようにしたもの」
くらいの理解から始めれば十分です。

my-recipe が使うのは `favorite_recipes` という **テーブル(表)** が1つだけです。

| id | title | genre | cooking_time | ... | created_at |
|---|---|---|---|---|---|
| a1b2... | 鶏むね肉と白菜の生姜炒め | 和食 | 20分 | ... | 2026-09-18 10:00 |
| c3d4... | 白菜のクリーム煮 | 洋食 | 25分 | ... | 2026-09-18 11:30 |

- **行(レコード)** = お気に入り1件
- **列(カラム)** = その1件が持つ項目

やることは4つしかありません。これを頭文字で **CRUD(クラッド)** と呼びます。

| 操作 | SQLでの命令 | my-recipeでは |
|---|---|---|
| Create(作る) | `INSERT` | お気に入り登録 |
| Read(読む) | `SELECT` | お気に入り一覧の表示 |
| Update(更新) | `UPDATE` | **使わない**(編集機能が無いため) |
| Delete(消す) | `DELETE` | お気に入り削除 |

💡 my-recipe が Update を持たないのは、設計で「編集機能は作らない」と決めたからです。
機能を減らすのも立派な設計判断です。作らないものを決めるほうが、実は難しい。

### Supabase とは

PostgreSQL(ポストグレスキューエル)という有名なデータベースを、
**Webから使える形で貸してくれるサービス** です。
自分でデータベースサーバーを立てる作業(数日かかる)が、登録5分で終わります。

## 1.5 API とは何か

APIは「プログラムがプログラムにお願いするための窓口」です。

人間向けの画面が「Webサイト」なら、プログラム向けの窓口が「API」。

```
人間 → 画面(HTML、見た目あり)
プログラム → API(JSON、見た目なし・データだけ)
```

### JSON(ジェイソン)

APIがやりとりするデータの書式です。JavaScriptのオブジェクトの書き方がそのまま
データ交換の標準になったものです。

```json
{
  "title": "鶏むね肉と白菜の生姜炒め",
  "cookingTime": "20分",
  "servings": "2人分",
  "ingredients": ["鶏むね肉 200g", "白菜 1/4個"],
  "steps": ["鶏むね肉を一口大に切る", "フライパンで炒める"]
}
```

ルールは少ないです。

- `{ }` で囲むと「まとまり(オブジェクト)」
- `[ ]` で囲むと「並び(配列)」
- `"キー": 値` の形で項目を書く
- 項目の区切りは `,`
- 文字列は必ず `"` (ダブルクォート)で囲む

my-recipe では、この形のJSONが3か所を流れます。

1. ブラウザ → 自分のサーバー: `{ "ingredients": ["鶏むね肉","白菜"], "genre": "和食" }`
2. 自分のサーバー → Claude API: 食材を含む指示文
3. Claude API → 自分のサーバー → ブラウザ: 上のレシピJSON

### HTTPメソッド

リクエストには「種類」があります。よく使うのは2つだけです。

| メソッド | 意味 | 例 |
|---|---|---|
| `GET` | ください(取得) | ページを開く、お気に入り一覧を取る |
| `POST` | これを処理して(送信) | 食材を送ってレシピを作ってもらう |

⚠️ 「ページを開く」は必ずGETです。だから **GETで課金処理をしてはいけません**。
ブラウザが勝手に先読みすることがあるからです。
my-recipeでレシピ生成をPOSTにしているのは、これが理由の1つです。

### ステータスコード

レスポンスには3桁の番号が付いてきます。

| 番号 | 意味 | よく見るやつ |
|---|---|---|
| 200 | 成功 | OK |
| 400 | **お願いの仕方が悪い**(クライアントのミス) | 食材が空っぽ |
| 404 | そんなページ無い | URLの打ち間違い |
| 500 | **サーバー側が壊れた** | AIの呼び出しに失敗 |

400番台か500番台かで、**自分のどちらのコードを疑うか** が変わります。
エラーを読むとき、まずここを見る癖をつけてください。

## 1.6 my-recipe の1回の操作を、最後まで追いかける

全部つなげます。利用者が「レシピを考えてもらう」を押した瞬間の旅です。

```
[1] ブラウザ
    利用者が「鶏むね肉, 白菜」と入力してボタンを押す
    ↓ 入力チェック(空じゃないか、10個以内か)
    ↓ POST /api/generate-recipe  body: {"ingredients":["鶏むね肉","白菜"],"genre":"和食"}
[2] Vercel上のNext.js(サーバー)
    ↓ 受け取った値をもう一度チェック(ブラウザのチェックは信用しない)
    ↓ 環境変数からAPIキーを取り出す
    ↓ Claude APIへ「この食材でレシピ考えて。この形のJSONで返して」
[3] Claude API
    ↓ 考える(1〜3秒)
    ↓ レシピJSONを返す
[2] Next.js
    ↓ 形が正しいか確認
    ↓ 200 OK + レシピJSON をブラウザへ
[1] ブラウザ
    受け取ったJSONを画面に描画する
```

そして「お気に入り登録」を押すと、別の旅が始まります。

```
[1] ブラウザ: ボタンを押す
[2] Next.jsサーバー: Supabaseへ INSERT
[3] Supabase: 1行保存して「OK」
[2] → [1]: 「登録しました」に表示を変える
```

**この2つの旅を、この教材ではそれぞれ Step4〜5、Step6 で作ります。**

🖐 **考えてみよう**
「お気に入り一覧を開く」ときは、誰から誰へ、どんなリクエストが飛ぶでしょうか。
Claude APIは登場するでしょうか。紙に矢印を書いてみてください。

<details>
<summary>答え</summary>

ブラウザ → Next.jsサーバー(GET /favorites)→ Supabase(SELECT)→ Next.js →
HTMLを組み立ててブラウザへ。**Claude APIは登場しません。**
保存済みのレシピを表示するだけなので、AIに聞く必要がないからです。
ここでAIを呼んでしまうと、一覧を開くたびにお金がかかります。
</details>

## 1.7 この章のまとめ

- Webアプリは **リクエストとレスポンスの往復** でできている
- 登場人物は **ブラウザ / サーバー / データベース / 外部API** の4つ
- **秘密情報(APIキー)はサーバーにだけ置く**。これは設計の最重要ルール
- データベースにやることは **CRUD** の4つだけ(今回はUpdate抜きの3つ)
- APIは **JSON** でやりとりする。`GET`は取得、`POST`は送信
- ステータスコードの **400番台はクライアントのミス、500番台はサーバーの故障**
