# 23. Vercel — なぜpushしただけで公開されるのか

> この章のゴール: Vercelが何をしているサービスなのかを理解し、
> 設定画面の各項目が「何のためにあるか」を説明できるようになる。

18章では手順どおりに登録しました。この章はその **中身** です。

---

## 23.1 Vercelは何を代行しているサービスなのか

自分でWebアプリを公開しようとすると、本来これだけの作業が必要です。

| # | やること | 自前でやると |
|---|---|---|
| 1 | サーバーを用意する | クラウドで仮想マシンを借りる |
| 2 | OSとNode.jsを入れる | 手作業。セキュリティ更新も自分で |
| 3 | コードを送り込む | 転送の仕組みを作る |
| 4 | `npm install` と `npm run build` | 自動化スクリプトを書く |
| 5 | アプリを常時起動させる | プロセス管理を設定 |
| 6 | 落ちたら再起動させる | 監視の仕組み |
| 7 | ドメインを繋ぐ | DNS設定 |
| 8 | HTTPS証明書を取得・更新 | 90日ごとの自動更新を設定 |
| 9 | 世界中から速く見えるようにする | CDNを契約・設定 |
| 10 | アクセスが増えたら増強する | 負荷分散の設計 |

**Vercelは、この1〜10を全部やります。** あなたがやるのは `git push` だけです。

💡 このような「サーバーの存在を意識しなくていい」形態を
**サーバーレス** や **PaaS(Platform as a Service)** と呼びます。
サーバーが無いわけではなく、**あなたが管理しなくていい** という意味です。

## 23.2 なぜ push すると自動でデプロイされるのか

ここが一番の疑問だと思います。**魔法ではなく、Webhookという仕組み** です。

### 仕組みの全体像

```
【準備段階:一度だけ】
  あなた: VercelにGitHubアカウントを連携
     ↓
  GitHub: 「Vercel」というGitHub Appをリポジトリにインストール
     ↓
  これにより、GitHubは「このリポジトリに変化があったらVercelに知らせる」
  という約束を持つ

【以降:毎回】
① あなた: git push
② GitHub: コードを受け取る
③ GitHub: 「変化がありました」とVercelのURLへ通知を送る  ← Webhook
④ Vercel: 通知を受け取り、そのリポジトリをコピー(clone)
⑤ Vercel: npm install → npm run build を実行
⑥ Vercel: 成果物を世界中のサーバーに配置
⑦ Vercel: URLを新しいものに切り替える
```

### Webhookとは

**「何かが起きたら、指定のURLに知らせてください」という予約** のことです。

```
通常のAPI :  こちらから「何かあった?」と聞きに行く(ポーリング)
Webhook  :  向こうから「ありましたよ」と教えに来る
```

⚠️ **VercelがGitHubを定期的に見張っているわけではありません。**
GitHubが、変化した瞬間にVercelを叩いています。だから数秒で反応します。

### GitHub App が持っている権限

連携したとき、あなたは GitHub App に権限を与えています。

| 権限 | 何に使われるか |
|---|---|
| リポジトリの読み取り | コードをコピーしてビルドする |
| Webhookの受信 | pushやPRの検知 |
| PRへのコメント | プレビューURLの自動投稿 |
| コミットステータスの書き込み | GitHub上に「デプロイ成功/失敗」を表示 |

💡 PRを作ると自動でVercelがコメントを付けるのは、この権限のおかげです。
**GitHubとVercelは、あなたが繋いだから会話できている** のであって、
最初から繋がっているわけではありません。

### 連携を確認・解除する場所

- GitHub側: Settings → Integrations → Applications → Vercel
- Vercel側: プロジェクト → Settings → Git

## 23.3 ビルドの中で何が起きているか

Vercelのダッシュボードで、デプロイのログを開いてみてください。だいたいこうなっています。

```
Cloning github.com/あなた/my-workspace (Branch: main, Commit: 935821c)
Running "install" command: `npm install`...
added 312 packages in 18s
Running "build" command: `npm run build`...
  ▲ Next.js 15.x.x
  Creating an optimized production build ...
  ✓ Compiled successfully
  ✓ Collecting page data
  ✓ Generating static pages (3/3)
Route (app)                    Size     First Load JS
┌ ○ /                          2.1 kB   105 kB
├ ƒ /api/generate-recipe       0 B      0 B
└ ƒ /favorites                 1.4 kB   102 kB
Build Completed in /vercel/output [45s]
Deploying outputs...
Deployment completed
```

### 各段階の意味

| 段階 | 内容 |
|---|---|
| **Cloning** | GitHubからコードをコピー。どのブランチ・どのコミットかが記録される |
| **install** | `package.json` を見て部品をダウンロード |
| **build** | `next build` を実行。TypeScriptの変換・最適化・静的ページの生成 |
| **Deploying** | 成果物を配置して、URLを切り替える |

⚠️ **17章で `npm run build` をローカルで試したのは、この段階を先取りするためです。**
ローカルで落ちるものは、ここでも必ず落ちます。

### ビルド結果の2種類

ログの `○` と `ƒ` の意味が、ここで効いてきます。

| 記号 | 種類 | どこに置かれるか | いつ実行されるか |
|---|---|---|---|
| `○` | 静的 | **世界中のCDN(エッジ)** | ビルド時に1回だけ作られる |
| `ƒ` | 動的 | **サーバーレス関数** | アクセスのたびに実行 |

```
利用者 → エッジ(東京など)
           ├─ 静的ファイル(CSS/JS/画像/静的ページ)→ ここで即返す。速い
           └─ 動的ページ・API → サーバーレス関数を起動して実行
```

my-recipe では:

- `/` … `○`。中身はブラウザ側で動く(`"use client"`)ので、HTMLは固定でよい
- `/favorites` … `ƒ`。DBの中身で変わるので毎回実行(`force-dynamic` の効果)
- `/api/generate-recipe` … `ƒ`。当然、毎回実行

💡 **静的にできるものは静的にするほど速く、安くなります。**
Next.jsが「できるだけ静的にしよう」とするのはこのためで、
15章で `force-dynamic` を明示的に書いたのは、それを **意図的に止めた** ということです。

### サーバーレス関数とは

「アクセスが来たときだけ起動して、処理して、終了するプログラム」です。

| | 従来のサーバー | サーバーレス |
|---|---|---|
| 起動 | ずっと動いている | 呼ばれたときだけ |
| 料金 | 動いている時間ぶん | **実行した回数・時間ぶん** |
| アクセス増加時 | 自分で増強する | **自動で並列に増える** |
| 初回の遅さ | 無い | **起動に少し時間がかかる**(コールドスタート) |

⚠️ 実行時間には上限があります(プランによる)。
AIの呼び出しが長引くと **504(タイムアウト)** になることがあります。
my-recipeが「ストリーミングを使わない」と設計で決めたのは、
出力が1,000トークン程度と短く、この上限に余裕があるからです(詳細設計書 3.1)。

## 23.4 デプロイの種類 — Production と Preview

Vercelは、**ブランチによって扱いを変えます**。

| push先 | 種類 | URL | 用途 |
|---|---|---|---|
| `main`(Production Branch) | **Production** | 本番ドメイン | 本番 |
| それ以外のブランチ | **Preview** | ブランチ用の一時URL | 確認用 |

だから 18章で「ブランチを使った安全な進め方」を紹介しました。
**本番を壊さずに、本物の環境で確認できます。**

### Production Branch の設定場所

**Settings → Git → Production Branch**

既定は `main` です。ここを変えると「どのブランチが本番か」が変わります。

⚠️ この設定を知らないと、
「`develop` にpushしたのに本番が変わらない」「main にpushしたら本番が変わってしまった」
という混乱が起きます。

### デプロイは「積み重なる」

**Vercelは、過去のデプロイを消しません。** 1回のデプロイごとに固有のURLが作られ、
そのまま残ります。

```
本番ドメイン  my-recipe-gold-ten.vercel.app
                    │ 今はここを指している(エイリアス)
                    ▼
デプロイ#43  my-recipe-a1b2c3-team.vercel.app  ← 最新
デプロイ#42  my-recipe-x9y8z7-team.vercel.app  ← 1つ前(まだ生きている)
デプロイ#41  ...
```

この構造のおかげで、**ロールバック(切り戻し)が一瞬** です。

> Deployments → 戻したいデプロイ → 「Promote to Production」または「Instant Rollback」

ビルドし直さず、**指し先を変えるだけ** なので数秒で戻ります。

⚠️ **18章で「デプロイ固有URLで動作確認するな」と書いた理由が、ここで繋がります。**
固有URLは「開発者が中身を確認するためのもの」なので、
既定で **Vercelへのログインが必要な保護** がかかっています。
本番ドメイン(短いほう)には、その保護がかかりません。

## 23.5 環境変数の設定 — ここが最も詰まる

**Settings → Environment Variables**

### 3つの環境スコープ

登録するとき、どの環境で使うかを選びます。

| スコープ | 適用先 |
|---|---|
| **Production** | 本番デプロイ |
| **Preview** | ブランチのプレビューデプロイ |
| **Development** | `vercel dev` を使うローカル開発(通常は `.env.local` を使うので不要) |

⚠️ **Production にだけ登録すると、プレビュー環境で動きません。**
「mainでは動くのに、ブランチのプレビューだと500になる」の典型的な原因です。
個人開発なら、**Production と Preview の両方にチェック** を入れておくのが無難です。

### ⚠️ 変更しても、すぐには反映されない

環境変数を追加・変更したあとは、**再デプロイが必要** です。

> Deployments → 最新のデプロイの「…」→ Redeploy

理由は2つあります。

| 変数の種類 | いつ使われるか | 変更時に必要なこと |
|---|---|---|
| `ANTHROPIC_API_KEY` など(サーバー専用) | 実行時に読まれる | 再デプロイ(関数の再作成) |
| **`NEXT_PUBLIC_` 付き** | **ビルド時にコードへ埋め込まれる** | **必ずビルドし直す** |

💡 `NEXT_PUBLIC_` の変数は、ビルド時に「文字列として置換」されています。
だから、**ビルド済みの成果物を差し替えない限り、古い値のまま** です。
「値を直したのに変わらない」の原因はこれです。

### 値の確認

登録済みの値は、既定では伏せ字になっています。
必要なら目のアイコンで表示できますが、**画面共有中は絶対に押さないでください**。

## 23.6 主要な設定項目の一覧

Settings 配下の項目を、「何のためにあるか」で整理します。

### General

| 項目 | 意味 | my-recipeでの設定 |
|---|---|---|
| **Framework Preset** | どのフレームワークか。ビルド方法が決まる | Next.js(自動検出) |
| **Root Directory** | リポジトリのどこにアプリがあるか | **`my-recipe`**(リポジトリ直下ではないため) |
| **Build Command** | ビルドに使うコマンド | 既定(`next build`) |
| **Output Directory** | 成果物の場所 | 既定 |
| **Install Command** | 依存の取得方法 | 既定(`npm install`) |
| **Node.js Version** | 実行環境のバージョン | 既定 |

⚠️ **Root Directory は、モノレポ(1つのリポジトリに複数プロジェクト)で必須** です。
`my-workspace` リポジトリには `my-recipe` `kakeibo` など複数あるので、
これを指定しないと「package.jsonが見つかりません」で失敗します。

### Domains

独自ドメインを繋ぐ場所です。

1. `my-recipe.com` などを取得(ドメイン業者、またはVercelで購入)
2. Vercelの Domains に追加
3. Vercelが指示するDNSレコード(AまたはCNAME)を、ドメイン業者側で設定
4. Vercelが所有を確認 → **HTTPS証明書を自動取得**
5. 反映までDNSの伝播時間がかかる(22章)

### Deployment Protection

**「誰がこのデプロイを見られるか」の設定です。**

| 保護 | 内容 |
|---|---|
| **Vercel Authentication** | Vercelアカウントでログインした人だけ閲覧可。**プレビューには既定でON** |
| **Password Protection** | パスワードを知る人だけ閲覧可(**プランにより利用可否が異なる**) |
| **Protection Bypass for Automation** | 自動テストなどが保護を通り抜けるための専用トークン |

⚠️ my-recipe は「URLを知る人は誰でも操作できる」という制約を受け入れた設計です
(要件定義 3.3)。それが嫌なら、ここで本番にも保護をかけます。
**利用できる保護の種類はプランによって変わるので、実際の画面で確認してください。**

### Functions

サーバーレス関数の設定です。

| 項目 | 意味 |
|---|---|
| **Function Region** | サーバー処理をどこで動かすか。**Supabaseと揃えると速い**(22章) |
| **Max Duration** | 実行時間の上限。超えると504 |

### Git

| 項目 | 意味 |
|---|---|
| **Production Branch** | どのブランチを本番とするか |
| **Ignored Build Step** | 特定の変更のときビルドをスキップする条件 |

💡 **Ignored Build Step** はモノレポで効きます。
`kakeibo` だけ変更したときに `my-recipe` のビルドを走らせない、といった設定ができます。
無駄なビルド時間(=無料枠の消費)を減らせます。

## 23.7 ログの見方

**問題が起きたときに見る場所は2つです。**

### ① Build Logs(ビルド時)

> Deployments → 該当のデプロイをクリック

デプロイ自体が失敗したときはここ。`npm run build` の出力がそのまま出ます。

| よくある失敗 | 原因 |
|---|---|
| `Cannot find module` | importのパス誤り、**大文字小文字の違い**(ローカルはMac、Vercelは Linux) |
| `Type error:` | TypeScriptの型エラー |
| `No package.json found` | **Root Directory の設定漏れ** |

### ② Runtime Logs(実行時)

> プロジェクト → Logs

デプロイは成功したのに動かないときはここ。
**`console.log` / `console.error` の出力がここに出ます**(20章)。

```ts
} catch (e) {
  console.error("レシピ生成に失敗:", e);   // ← ここに出る
  return NextResponse.json({ error: "..." }, { status: 500 });
}
```

⚠️ **ログに秘密情報を出さないでください。** APIキーやDBの接続情報を
`console.log` すると、ログに残ります。デバッグで一時的に出したら、必ず消します。

## 23.8 料金プランの考え方

| プラン | 対象 | 重要な点 |
|---|---|---|
| **Hobby** | 個人の **非商用** プロジェクト | 無料。⚠️ **商用利用は規約で認められていない** |
| **Pro** | 個人・小規模チームの商用 | 有料(ユーザー単位の月額) |
| **Enterprise** | 大規模組織 | 個別見積もり |

### ⚠️⚠️ ここは商用化で最も重要な点です

**Hobbyプランは「非商用」限定です。** 広告を載せる、課金する、業務で使う、
といった場合は **Proプランへの移行が必要** です。

my-recipe は個人利用なのでHobbyで問題ありませんが、
**もし人に売る・広告を出すなら、まずここが変わります**(25章で再度扱います)。

### 消費される資源

プランごとに上限があります(具体的な数値は変わるので、ダッシュボードで確認してください)。

| 資源 | 何に使われるか |
|---|---|
| 帯域幅 | 配信したデータ量 |
| 関数の実行時間 | サーバー処理の合計時間 |
| ビルド時間 | デプロイのたびに消費 |
| 同時ビルド数 | Hobbyは1つずつ |

💡 **個人利用でこれらを使い切ることは、まずありません。**
気にすべきは、むしろ **Anthropic APIの従量課金** のほうです。

## 23.9 チームが必要な理由

18章で「Vercelでプロジェクトを作るにはチームが必要」と書きました。

Vercelは、プロジェクトの所有単位を **Team(スコープ)** で管理しています。
個人アカウント単体だと、この所有者が定まらず、
プロジェクト作成や一部の操作ができない場合があります。

⚠️ **チーム作成自体は無料(Hobby相当)です。**
作成時にProプランを勧められますが、選ばなくて構いません。

💡 チームを新しく作った直後は、外部ツール(Claudeのコネクタなど)が
そのチームを認識しないことがあります。認可時点の情報がキャッシュされているためで、
**接続を切って繋ぎ直すと解決** します。

## 23.10 Vercelができないこと

「何でもやってくれる」わけではないので、境界を知っておきます。

| できないこと | どうするか |
|---|---|
| データを永続的に保存する | **Supabase等のDBを使う**(24章) |
| ファイルを保存する | Vercel Blob、Supabase Storage、S3など |
| 長時間動き続ける処理 | 別のサービス(ジョブ実行基盤)へ |
| **環境変数をAPI経由で登録する** | ⚠️ **ダッシュボードから手作業**(自動化ツールからは登録できない場合がある) |
| メールを送る | **専用サービスが必要**(25章) |

⚠️ サーバーレス関数は **処理が終わると消えます**。
ファイルを書き出しても次のリクエストでは存在しません。
**「サーバーに保存する」という発想が通用しない** のが、最も大きな違いです。

## 23.11 この章のまとめ

- Vercelは **サーバー調達からHTTPS・CDNまでを代行** するサービス
- **push で自動デプロイされるのは Webhook のおかげ**。
  GitHub App を入れたから、GitHubがVercelに通知している
- ビルドの結果は **静的(エッジ配信)** と **動的(サーバーレス関数)** に分かれる
- `main` は Production、他のブランチは Preview
- デプロイは積み重なるので **ロールバックが一瞬**
- ⚠️ 環境変数は **Production / Preview の両方** に登録し、**変更後は再デプロイ**
- ⚠️ `NEXT_PUBLIC_` は **ビルド時に埋め込まれる** ので、必ずビルドし直す
- Root Directory はモノレポで必須
- 問題が起きたら **Build Logs(デプロイ失敗)** と **Runtime Logs(実行時)**
- ⚠️ **Hobbyプランは非商用限定**。商用ならProへ
- サーバーレス関数に **ファイルを保存しても消える**
