# 22. ネットワークの基礎 — 各サービスはどう繋がっているのか

> この章のゴール: URLをタップしてから画面が出るまでに何が起きているかを追え、
> 「Vercel・Supabase・Anthropicが、どういう関係で動いているか」を説明できるようになる。

01章では登場人物を紹介しました。この章は **その間を通っている線**、つまり
ネットワークの話です。ここが分かると、「なぜサーバー側なら安全なのか」
「なぜ環境変数を分けるのか」が、腑に落ちる形で理解できます。

---

## 22.1 まず、住所の話から

### URLの構造

```
https://my-recipe-gold-ten.vercel.app/favorites?genre=和食
└─┬─┘   └────────────┬────────────┘└───┬───┘└────┬────┘
 ①       ②                ③            ④

① スキーム      … 通信のしかた(https = 暗号化されたhttp)
② ホスト名      … どのコンピューターか(ドメイン名)
③ パス          … その中のどこか
④ クエリ        … 追加の注文
```

住所に例えると、②が「建物」、③が「部屋番号」、④が「窓口での要望」です。

⚠️ 実は、ここに **ポート番号** が隠れています。

```
https://example.com/         ← 省略されているが :443
http://example.com/          ← 省略されているが :80
http://localhost:3000        ← 開発中はこれ。省略していない
```

| 要素 | 役割 |
|---|---|
| **IPアドレス** | コンピューターの住所(`76.76.21.21` のような番号) |
| **ポート番号** | そのコンピューターの中の「窓口番号」 |

1台のコンピューターで、Webサーバー(443番)もデータベース(5432番)も
同時に動かせるのは、**窓口を分けているから** です。

💡 開発中に `localhost:3000` と打つのは「自分のPCの3000番窓口」という意味でした(02章)。
`npm run dev` が2つ動かないのは、同じ窓口を2人で使えないからです。

## 22.2 DNS — 名前からIPアドレスを調べる

コンピューター同士は **IPアドレス(数字)** でしか通信できません。
でも人間は `my-recipe.vercel.app` のような名前で覚えます。

この **名前 → 数字の変換** をするのが **DNS(Domain Name System)** です。
電話帳だと思ってください。

```
ブラウザ: 「my-recipe-gold-ten.vercel.app の番号を教えて」
   ↓
DNSサーバー: 「76.76.21.21 です」
   ↓
ブラウザ: その番号に接続しに行く
```

### なぜこれを知る必要があるか

**独自ドメインを設定するとき、まさにこの仕組みを触るから** です。

たとえば `my-recipe.com` を買って Vercel に繋ぐとき、
ドメイン管理画面で「このドメインの行き先はVercelです」というレコードを登録します。

| レコード種類 | 意味 | 使う場面 |
|---|---|---|
| **A** | この名前は、このIPアドレス | ルートドメイン(`example.com`) |
| **CNAME** | この名前は、別の名前の別名 | サブドメイン(`www.example.com`) |
| **MX** | このドメイン宛のメールは、このサーバーへ | **メール受信**(25章で扱います) |
| **TXT** | 自由なテキスト。所有証明などに使う | **メール送信の認証**(SPF/DKIM/DMARC) |

⚠️ DNSの変更は **すぐには反映されません**。世界中のDNSサーバーが
結果を一定時間キャッシュしているためです(**TTL** という設定で決まる)。
数分〜数時間かかることがあります。「設定したのに繋がらない」の多くは、
**間違いではなく、待ち時間** です。

## 22.3 HTTPS — なぜ「s」が付くと安全なのか

### HTTPだけだと何が起きるか

インターネットの通信は、**途中にたくさんの機器を経由** します。

```
あなたのスマホ → Wi-Fiルーター → 回線業者 → 中継地点 → … → サーバー
                    ↑ここも   ↑ここも   ↑ここも  全部、中身が見える
```

HTTPは中身が平文なので、**経路上の誰でも読めますし、書き換えられます**。
カフェのフリーWi-Fiでパスワードを送るのが危ない、と言われるのはこれが理由です。

### HTTPSがやっていること

HTTPSは、HTTPの下に **TLS** という暗号化の層を敷きます。やることは3つ。

| | 内容 | 防ぐもの |
|---|---|---|
| **暗号化** | 中身を第三者が読めなくする | 盗み見 |
| **改ざん検知** | 途中で書き換えられたら分かる | すり替え |
| **サーバー認証** | 相手が本物のサーバーだと確認する | なりすまし |

3つ目が **証明書** の役割です。

```
ブラウザ: 「あなたが本当に vercel.app か証明して」
サーバー: 「これが証明書です」(認証局が発行した身分証)
ブラウザ: 認証局のサインを確認 → OK → 暗号化通信を開始
```

🔒 ブラウザのアドレス欄の鍵マークは、この確認が通った印です。

### my-recipe で証明書はどうなっているか

**何もしていません。Vercelが自動で用意しています。**

かつては証明書の取得に手続きとお金が必要でしたが、今は
Let's Encrypt などの仕組みで無料かつ自動になりました。
Vercelは、独自ドメインを繋いだ場合でも **自動で証明書を取得・更新** します。

⚠️ 逆に言うと、**証明書には有効期限があります**(通常90日)。
自前でサーバーを立てる場合、この更新を自動化しないと
「ある日突然、全ユーザーに警告が出る」という事故になります。
**Vercelを使う利点の1つが、これを考えなくていいこと** です。

## 22.4 1回のリクエストが辿る全経路

ここまでを繋げます。スマホで `my-recipe` を開いた瞬間の、完全な流れです。

```
【1】 スマホのブラウザ
      「my-recipe-gold-ten.vercel.app を開きたい」
        │
        │ DNSに問い合わせ
        ▼
【2】 DNSサーバー
      「76.76.21.21 です」(実際はVercelのエッジの入口)
        │
        ▼
【3】 TCP接続 + TLSハンドシェイク
      443番ポートに接続し、証明書を確認して暗号化路を作る
        │
        │ GET / HTTP/1.1
        ▼
【4】 Vercelのエッジ(世界中にある入口。日本なら東京付近)
      ・静的ファイル(CSS/JS/画像)ならここで即返す ← 速い理由
      ・サーバー処理が必要なら、次へ
        │
        ▼
【5】 Vercelのサーバーレス関数(Next.jsのサーバー部分)
      ・ページを組み立てる
      ・必要ならSupabaseやAnthropicを呼ぶ  ← ここは【別の通信】
        │
        ▼
【6】 HTMLがブラウザへ返る
        │
        ▼
【7】 ブラウザがHTMLを解釈し、CSS/JSを追加で取りに行く(【4】に戻る)
        │
        ▼
【8】 JavaScriptが動き出す(ハイドレーション)
      → ここで初めてボタンが押せるようになる
```

### ⚠️ 【8】のハイドレーションが重要

サーバーが返すのは **HTML(静止画のようなもの)** です。
その後にJavaScriptが読み込まれ、**ボタンにクリック処理を取り付けて**
初めてアプリとして動きます。これを **ハイドレーション(水を与える)** と呼びます。

だから、**画面は正しく見えているのにクリックが一切効かない**、
という現象が起こりえます(JSの読み込みに失敗した場合)。
19章の自動試験の注意点は、これが理由でした。

## 22.5 「サーバー側から呼ぶ」の本当の意味

01章で「APIキーはサーバー側から使う」と学びました。
ネットワークの視点で見ると、こういうことです。

### ブラウザから直接呼ぶ場合(✕)

```
【利用者のスマホ】
  my-recipeのJSコード(APIキー入り)
      │
      │ ① キーはコードに書いてある = F12で読める
      │ ② 通信もF12のNetworkタブで見える
      ▼
  api.anthropic.com
```

**キーが2か所で丸見え** です。暗号化(HTTPS)されていても関係ありません。
暗号化は「経路の途中の第三者」から守るものであって、
**送信者本人(=利用者)からは当然見えます**。

⚠️ ここは誤解が多いところです。
**HTTPSは、利用者自身からブラウザの中身を隠す機能ではありません。**

### サーバー経由で呼ぶ場合(○)

```
【利用者のスマホ】
  my-recipeのJSコード(キーは入っていない)
      │
      │ 「鶏むね肉と白菜でレシピを」だけ送る
      ▼
【Vercelのサーバー】 ← 利用者は中に入れない
  環境変数からキーを読む
      │
      │ この通信は、利用者からは完全に見えない
      ▼
  api.anthropic.com
```

**Vercelのサーバーの中は、利用者からは観測できません。**
だから、そこに置いた秘密は秘密のままでいられます。

💡 `NEXT_PUBLIC_` を付けると、**ビルド時にJSファイルの中に埋め込まれます**。
だから「ブラウザに公開される」わけです。付けなければ埋め込まれないので、
そもそもブラウザ側のコードに存在しません。

## 22.6 オリジンとCORS — なぜ「同じサイト」だけ許されるのか

### オリジンとは

```
https://my-recipe.vercel.app
└─┬─┘  └────────┬──────┘
スキーム    ホスト      (+ポート)

この3つの組み合わせ = オリジン
```

ブラウザには **同一オリジンポリシー** という安全装置があります。

> **あるサイトのJavaScriptは、原則として別のオリジンへ勝手に通信できない**

理由を考えてみてください。もしこれが無いと、
悪意のあるサイトを開いただけで、そのページのJavaScriptが
あなたのログイン済みの銀行サイトにアクセスできてしまいます。

### CORS

とはいえ、正当な理由で別オリジンを呼びたいこともあります。
そのとき、**呼ばれる側が「このオリジンなら許可します」と宣言する** 仕組みが
**CORS(Cross-Origin Resource Sharing)** です。

```
ブラウザ: 「https://my-app.com から呼びたいけど、いい?」
相手サーバー: 「Access-Control-Allow-Origin: https://my-app.com」→ 許可
```

### my-recipe でCORSエラーが出ない理由

```
画面        : https://my-recipe.vercel.app/
API呼び出し : /api/generate-recipe   ← 同じオリジン!
```

`fetch("/api/generate-recipe")` のように **相対パス** で書いているので、
同じオリジンへの通信です。だからCORSは一切関係ありません。

⚠️ **Next.jsで画面とAPIを同居させる構成の、地味だが大きな利点** です。
フロントとバックを別々のサービスに置くと、CORS設定が必ず必要になり、
初心者が最も苦しむポイントの1つになります。

💡 Supabaseへの通信も、**サーバー側(Server Actions)から行っている** ので
ブラウザの同一オリジンポリシーの対象外です。
ブラウザから直接Supabaseを呼ぶ構成もありますが、その場合は
SupabaseがCORSを許可する設定になっています。

## 22.7 3つのサービスの関係を、改めて整理する

```
                    ┌──────────────────────┐
                    │   利用者のブラウザ      │
                    └──────────┬───────────┘
                               │ ① HTTPS
                               │   画面を要求 / 食材を送信
                               ▼
        ┌──────────────────────────────────────────┐
        │  Vercel                                   │
        │  ・GitHubのコードをビルドして配置          │
        │  ・静的ファイルを世界中のエッジから配信    │
        │  ・サーバー処理(Next.js)を実行           │
        │  ・環境変数(秘密情報)を保持              │
        └───────┬──────────────────────┬───────────┘
                │ ② HTTPS               │ ③ HTTPS
                │  anonキーで            │  APIキーで
                ▼                       ▼
    ┌───────────────────┐   ┌───────────────────────┐
    │  Supabase          │   │  Anthropic             │
    │  ・PostgreSQL      │   │  ・Claude API          │
    │  ・RLSで行単位制御 │   │  ・従量課金            │
    │  ・データを永続化  │   │  ・状態を持たない      │
    └───────────────────┘   └───────────────────────┘

        ┌───────────────────┐
        │  GitHub            │ ── ④ push を検知 ──> Vercel
        │  ・コードの保管庫  │
        └───────────────────┘
```

### 各サービスの「担当」を一言で

| サービス | 担当 | 無くなったらどうなるか |
|---|---|---|
| **GitHub** | コードの保管と履歴 | 新しくデプロイできない(動いているアプリは生きている) |
| **Vercel** | アプリの実行と配信 | **アプリが開けない** |
| **Supabase** | データの保管 | お気に入りが見られない(レシピ生成はできる) |
| **Anthropic** | レシピの生成 | レシピが作れない(お気に入りは見られる) |

💡 **役割が分離していると、壊れ方も分離します。**
「お気に入りだけ見られない」なら、疑うのはSupabaseだけ。
これは切り分けのうえで大きな利点です。

### 4種類の通信を区別する

| # | 通信 | 認証に使うもの | 利用者から見えるか |
|---|---|---|---|
| ① | ブラウザ → Vercel | なし(公開アプリ) | 見える |
| ② | Vercel → Supabase | anonキー | **見えない** |
| ③ | Vercel → Anthropic | APIキー | **見えない** |
| ④ | GitHub → Vercel | Webhook(23章で解説) | — |

⚠️ ①だけが「利用者が直接触る通信」です。
だから、**①に渡すものは全部公開されると考える** のが正しい設計の出発点です。

## 22.8 リージョンとレイテンシ — なぜ「東京」を選ぶのか

14章でSupabaseのRegionに「Northeast Asia (Tokyo)」を推奨しました。理由は物理です。

**データは光の速さでしか進みません。** 東京〜米国西海岸は約8,000km、
往復で最低でも80ms程度かかります。実際には中継機器があるのでもっとかかります。

```
利用者(日本) → Vercelエッジ(東京) : 数ms
Vercelの関数(米国) → Supabase(米国) : 数ms   ← 近い
Vercelの関数(米国) → Supabase(東京) : 往復150ms ← 遠い!
```

⚠️ **重要なのは「利用者とDBの距離」ではなく「サーバー処理とDBの距離」** です。
1回の画面表示でDBに3回問い合わせるなら、150ms × 3 = 450msの差が出ます。

💡 my-recipeは個人利用で、そもそもAI生成に2〜4秒かかるので、
この差は誤差の範囲です。ただし **商用で使うなら、サーバー処理とDBのリージョンを
揃えるのが原則** です(25章で再度触れます)。

## 22.9 ステータスコードをネットワーク視点で読み直す

01章で学んだ番号を、「誰が返したか」で分類します。

| コード | 誰が返したか | 意味 |
|---|---|---|
| 200 | アプリ | 成功 |
| **301 / 302** | Vercelやアプリ | 別のURLへ移動して、という指示 |
| 400 | アプリ | 送られてきた内容がおかしい |
| **401 / 403** | アプリ、または **Vercelの保護機能** | 権限がない |
| 404 | Vercel、またはアプリ | そのURLは存在しない |
| **429** | Anthropic、Vercel、Supabase | **短時間に呼びすぎ**(レート制限) |
| 500 | アプリ | アプリのコードが落ちた |
| **502 / 504** | **Vercelの基盤** | サーバー処理が起動しない/時間切れ |

⚠️ 見分けが重要な2つ:

- **403が突然全リクエストで出る** → アプリのバグではなく、
  **Vercelの保護機能が発動している** 可能性(19章の注意点)
- **504(タイムアウト)** → 処理が制限時間を超えている。
  Vercelのサーバーレス関数には実行時間の上限があります

💡 504は、AIの呼び出しを大量に並列でやったり、
巨大な処理を1リクエストで行ったときに出ます。
my-recipeは1回1件・数秒なので問題になりません。

## 22.10 この章のまとめ

- URLは **スキーム + ホスト + パス + クエリ**。裏にポート番号がある
- **DNS** が名前をIPアドレスに変換する。反映には時間がかかる
- **HTTPS** は 暗号化・改ざん検知・サーバー認証 の3つ。証明書はVercelが自動管理
- **ハイドレーション**が終わるまで、画面は見えていてもボタンは効かない
- ⚠️ **HTTPSは、利用者本人からブラウザの中身を隠すものではない**。
  だから秘密はサーバーに置く
- **同一オリジンポリシー**があるので別オリジンへは勝手に通信できない。
  my-recipeは画面とAPIが同居しているので **CORSが発生しない**
- 4種類の通信のうち、**利用者が触れるのは①だけ**。①に渡すものは公開される前提
- **サーバー処理とDBのリージョンを揃える** とレイテンシが減る
- ステータスコードは「誰が返したか」で読む。**403の多発はアプリのバグとは限らない**
