## 21.1 あなたが身につけたこと

作ったものを技術要素で分解すると、こうなります。

| 分野 | 具体的にできるようになったこと |
|---|---|
| **設計** | 要件定義 → 基本設計 → 詳細設計 の順で決める。やらないことを決める |
| **HTML/CSS** | 構造と見た目の分離。Flexbox。デザイントークン。レスポンシブ |
| **JavaScript** | 配列操作、非同期処理、エラーハンドリング |
| **TypeScript** | 型でデータの形を定義する。外部データを安全に扱う |
| **React** | コンポーネント分割、props、state、state の置き場所の判断 |
| **Next.js** | ルーティング、サーバー/クライアントの使い分け、API作成 |
| **データベース** | テーブル設計、SQL、RLS、CRUD |
| **外部API** | AIの呼び出し、プロンプト設計、構造化出力、コスト管理 |
| **セキュリティ** | 秘密情報の扱い、二重のバリデーション、ホワイトリスト |
| **運用** | Git、デプロイ、環境変数、ログの読み方、試験 |

**これは「Webアプリ開発の1周」です。** 各分野の深さはまだ浅いですが、
**全体の地図を持っている** という状態は、部分的に詳しいことよりずっと価値があります。

## 21.2 次にやるべきこと — 「2本目を作る」

**最も効果があるのは、教材を見ずに別のアプリを作ることです。**

写経で作ったものは、悲しいことに1か月で忘れます。
自分で決めながら作ると、忘れません。

### 題材の選び方

条件は3つ。

1. **自分が使いたいもの**(モチベーションが続く)
2. **画面2つ以内**
3. **テーブル1〜2個**

### 候補

| アプリ | テーブル | 新しく学べること |
|---|---|---|
| 読書記録 | `books` | 画像(表紙URL)、評価の星表示 |
| 筋トレ記録 | `workouts` | 日付での集計、グラフ表示 |
| 行きたい店リスト | `places` | 地図API、カテゴリ分類 |
| 英単語帳 | `words` | ランダム出題、正誤の記録 |
| AI日記要約 | `diaries` | AIで長文要約、月ごとの振り返り |

### 進め方(この教材の型をなぞる)

```
1. 要件定義を書く(30分)
   目的 / 利用者 / MUST 3つ / やらないこと / コスト
2. 画面とテーブルを決める(30分)
3. プロジェクトを作る
4. 動かない画面を作る
5. フォームを動かす
6. 偽データのAPIを作る
7. 本物に繋ぐ
8. DBに繋ぐ
9. CSS
10. デプロイ
11. 試験
```

⚠️ **1と2を飛ばさないでください。** 飛ばすと必ず途中で作り直しになります。
30分の設計が、半日の手戻りを防ぎます。

## 21.3 my-recipe を拡張してみる(演習)

2本目が重いなら、既存のものを改造するのも良い練習です。
**難易度順** に並べます。

### ★☆☆ お気に入りの件数を表示する

```
お気に入り(12件)
```

**ヒント**: `favorites.length` を表示するだけ。
絞り込み時は絞り込み後の件数になる点に注意。

---

### ★☆☆ 「使った食材」で検索できるようにする

お気に入り一覧に検索ボックスを追加します。

**ヒント**: Supabaseの `.ilike("source_ingredients", "%" + q + "%")` を使います。
ジャンル絞り込みと同じく、**URLのクエリパラメータ** で状態を持つのがおすすめです。

---

### ★★☆ お気に入りの並び替え

「新しい順 / 古い順 / 調理時間が短い順」を選べるようにします。

**ヒント**: `.order()` の引数を切り替えます。
調理時間は `text` 型で `"20分"` のように入っているので、**数値として並べ替えられません**。
ここで「データ型の設計ミス」に気づくはずです。
`cooking_time_minutes integer` 列を足すべきだった、という学びが得られます。

💡 **これは非常に良い演習です。** 設計判断が後から響く、という実感が得られます。

---

### ★★☆ レシピを編集できるようにする

要件定義で「やらない」と決めた機能です。あえて足してみます。

**必要なこと**:
1. RLSに **UPDATEポリシーを追加**(今は無いので拒否される)
2. `updateFavorite` Server Action
3. 編集フォームのUI

⚠️ 14章で「UPDATEポリシーを作らない」と決めた意味が、ここで分かります。
**設計で機能を絞ると、セキュリティ設定まで単純になる。**

---

### ★★★ ログイン機能を付ける

最大の拡張です。要件定義 3.3 で意図的に外したものです。

**必要なこと**:
1. Supabase Auth でログイン画面を作る
2. `favorite_recipes` に `user_id` 列を追加
3. **RLSポリシーの条件を差し替える**

```sql
-- 今
using (true)

-- ログイン後
using (auth.uid() = user_id)
```

💡 **`using (true)` を書いておいた設計が、ここで報われます**(14章)。
RLSが無効だったら、有効化から全部やり直しでした。

4. `middleware.ts` でセッションを扱う
5. サーバー/クライアント両方のSupabaseクライアントを用意する

★3つの理由は、**認証は状態管理が一気に複雑になる** からです。
ただし、これを乗り越えると作れるアプリの幅が大きく広がります。

---

### ★★★ 複数のレシピ候補から選べるようにする

要件定義のスコープ外にあった機能です。

**設計から考えてください**:
- AIに3つ返させる? 3回呼ぶ?(**コストが3倍になる**)
- 画面はどう見せる? カードを横に並べる? タブ?
- 選ばれなかった候補は保存する? しない?

⚠️ これは **実装より設計が難しい** 課題です。08章の考え方で整理してみてください。

## 21.5 AIとの付き合い方

この教材は「AIを使わずに作る」前提で書きました。
理由は、**AIに出してもらったコードを評価できるようになるため** です。

一周した今なら、AIを使っても中身が分かります。おすすめの使い方:

| 使い方 | 例 |
|---|---|
| ○ 分からない概念の説明 | 「Reactのkeyが必要な理由を、初心者向けに」 |
| ○ エラーの原因を聞く | エラーメッセージを貼って聞く |
| ○ 書いたコードのレビュー | 「このコードの問題点を指摘して」 |
| ○ 選択肢の比較 | 「AとBのどちらを選ぶべきか、判断軸ごとに」 |
| △ コードの生成 | **必ず読んで理解してから使う** |
| ✕ 丸投げ | 動かなくなったとき、何もできなくなる |

⚠️ **AIは「それらしいが間違っている」コードを出すことがあります。**
特にNext.jsのようにバージョンで作法が変わるものは、
**古い書き方を出してくることがよくあります**(`searchParams` の件など)。

**判断できる自分がいて初めて、AIは強力な道具になります。**
そのための一周でした。

## 21.6 最後に — 設計書を書く習慣について

この教材で一番覚えて帰ってほしいのは、文法ではなく **08章** です。

`docs/` の設計書を読み返してみてください。

- なぜログインを作らなかったのか
- なぜ材料を改行区切りの文字列で保存したのか
- なぜRLSを「無効」ではなく「全部許可」にしたのか
- なぜ Haiku を選んだのか

**全部に理由が書いてあります。**

コードは「何をしているか」しか語りません。
**「なぜそうしたか」は、書き残さないと必ず失われます。**

半年後の自分は他人です。その他人に向けて、
判断の理由を残しておく。これが、個人開発を「趣味」から
「ちゃんとしたもの作り」に変える、たった1つの習慣です。
