# 19. 試験 — 壊れていないことを確かめる

> この章のゴール: 「なんとなく動いた」ではなく、
> **何を確認したかを説明できる状態** にする。

---

## 19.1 なぜ試験をするのか

作った本人は、**正しい使い方しかしません**。
食材を2つ入れて、ボタンを押して、レシピが出た。動いた。……で終わりがちです。

でも実際に使われると、こういうことが起きます。

- 何も入力せずボタンを押す
- 食材を30個入れる
- 生成中にもう一度ボタンを押す
- 通信が切れた状態で送信する
- URLを直接書き換える
- スマホの縦画面で開く

**試験とは、これらを意図的にやってみる作業** です。

### もう1つの目的

半年後に機能を足したとき、**昔動いていた部分が壊れていないか** を確認できます。
試験項目が文書になっていれば、それをもう一度なぞるだけで済みます。
これを **回帰試験(リグレッションテスト)** と呼びます。

---

## 19.2 試験の観点 — 3種類を必ず作る

| 観点 | 意味 | 例 |
|---|---|---|
| **正常系** | 想定通りの使い方 | 食材2つでレシピ生成 |
| **異常系** | 間違った使い方・失敗 | 空入力、通信断 |
| **境界値** | 限界のちょうど際 | 食材0個 / 1個 / 10個 / 11個 |

⚠️ **初心者は正常系しか作りません。** バグの大半は異常系と境界値に潜みます。

### 境界値が効く理由

「10個まで」という仕様なら、バグは **必ず10と11の境目** にあります。

```
if (ingredients.length > MAX_INGREDIENTS)   ← 10個はOK、11個でエラー(正しい)
if (ingredients.length >= MAX_INGREDIENTS)  ← 10個でエラー(バグ)
```

5個や20個で試しても、この違いは見つかりません。
**「ちょうど境目」と「その1つ隣」を試す**。これが境界値試験です。

---

## 19.3 試験項目を書き出す

**実施する前に、紙(表)に書き出します。**
やりながら考えると、必ず漏れます。

各項目に必要なのは4つです。

| 列 | 内容 |
|---|---|
| No | `TC01` から連番 |
| 試験項目 | 何を確認するか |
| 試験手順 | どう操作するか(**他人が同じことをできる粒度で**) |
| 期待結果 | どうなれば合格か |

### my-recipe の試験項目(例)

| No | 試験項目 | 試験手順 | 期待結果 |
|---|---|---|---|
| TC01 | ホーム画面の初期表示 | 本番URLを開く | ヘッダー・入力欄・ジャンル選択・ボタンが表示され、レシピ結果は非表示 |
| TC02 | レシピ生成(正常系) | 「鶏むね肉, 白菜」を入力し、ジャンル「和食」で送信 | 3〜5秒後に、料理名・調理時間・人数・材料・作り方が表示される |
| TC03 | 食材未入力(異常系) | 何も入力せず送信 | 「食材を1つ以上入力してください。」が表示され、API呼び出しは発生しない |
| TC04 | 食材が上限(境界値) | 食材をちょうど10個入力して送信 | 正常にレシピが生成される |
| TC05 | 食材が上限超過(境界値) | 食材を11個入力して送信 | 「食材は10個までにしてください。」が表示される |
| TC06 | 全角読点での区切り | 「鶏むね肉、白菜」(全角読点)で送信 | カンマと同様に2つの食材として扱われる |
| TC07 | ジャンル指定 | ジャンル「イタリアン」で送信 | 結果のバッジが「イタリアン」になり、料理もイタリアン系になる |
| TC08 | 生成中の二重送信防止 | 生成中にボタンを再度押そうとする | ボタンが無効化されており押せない。表示は「考案中...」 |
| TC09 | 材料のチェック | 材料のチェックボックスを2つ押す | 打ち消し線が付く。リロードすると解除される |
| TC10 | 別レシピの再提案 | 「別のレシピを提案してもらう」を押す | 同じ食材・ジャンルで、**直前と異なる**レシピが表示される |
| TC11 | 再提案時の状態リセット | チェックと保存をした後に再提案する | チェックが外れ、ボタンが「お気に入り登録」に戻る |
| TC12 | お気に入り登録 | 「お気に入り登録」を押す | 「お気に入りに登録しました」に変わり、ボタンが押せなくなる |
| TC13 | お気に入り一覧表示 | ヘッダーの「お気に入り」を押す | 登録済みレシピが**新しい順**に、タイトルとジャンルのみ表示される |
| TC14 | 折りたたみの展開 | カードのタイトルを押す | 調理時間・人数・使った食材・材料・作り方が表示される |
| TC15 | ジャンル絞り込み | 「和食」を押す | URLに `?genre=和食` が付き、和食のみ表示される |
| TC16 | 絞り込みで0件 | 登録の無いジャンルを押す | 「このジャンルのお気に入りはありません。」が表示される |
| TC17 | お気に入り削除 | 削除ボタンを押す | 一覧から消え、Supabaseの該当行も消えている |
| TC18 | 未登録時の表示 | 0件の状態で一覧を開く | 「まだお気に入りがありません。」が表示される |
| TC19 | 不正なクエリパラメータ | `/favorites?genre=あああ` を直接開く | エラーにならず、全件表示される |
| TC20 | スマホ表示 | スマホ幅(375px)で全画面を確認 | 横スクロールが発生せず、入力欄・ボタンが縦に並ぶ |

### 「期待結果」の書き方のコツ

⚠️ **「正常に動く」「問題ない」と書かないでください。**
何をもって正常かが人によって変わり、試験になりません。

```
✕ レシピが正常に表示される
○ 料理名・調理時間・人数・材料・作り方の5項目がすべて表示される
```

**画面に何が出るか、具体的に書く。** これが試験項目の品質です。

## 19.4 異常系をどう起こすか

「Claude APIが失敗したとき」のような異常系は、普通には起こせません。
意図的に壊して確認します。

| 試したい状況 | 起こし方 |
|---|---|
| APIキーが無効 | `.env.local` のキーを1文字変えてローカルで実行 |
| 通信断 | F12 → Network → Throttling を「Offline」にする |
| DBエラー | Supabaseのキーを一時的に間違える |
| 遅いネットワーク | Network → Throttling を「Slow 4G」にする |

⚠️ **本番環境では試さないでください。** ローカルで確認します。
そして **確認したら必ず元に戻す**。

💡 「Slow 4G」での確認は地味に大事です。
高速な回線では一瞬で終わる処理も、遅い回線では
「考案中...」の状態が数秒続きます。その間の見た目が壊れていないか確認できます。

## 19.5 記録を残す

各項目について、実施した結果を記録します。

| 列 | 内容 |
|---|---|
| 実施結果 | 実際にどうなったか(**期待結果のコピペにしない**) |
| 判定 | OK / NG |

そして **画面のスクリーンショット** を残します。これを **エビデンス(証跡)** と呼びます。

### スクリーンショットの撮り方

- **画面全体(フルページ)** を撮る。切り抜かない
- 注目してほしい箇所は、**画像を加工せず**、
  後から赤い枠を重ねて示す(元画像は無加工で保管)

⚠️ 画像自体に書き込むと、後から「本当にこの画面だったのか」が確認できなくなります。
**元データは無加工、注釈は別レイヤー** が原則です。

### NG が出たら

1. **記録する**(隠さない)
2. 直す
3. **もう一度、最初から該当項目を実施する**
4. 結果を上書きせず、「修正後に再実施してOK」と分かる形で残す

💡 試験は「合格させる作業」ではなく「**実態を明らかにする作業**」です。
NGが出るのは失敗ではなく、試験が機能している証拠です。

## 19.6 試験成績書としてまとめる

my-workspace では、試験結果を **1つのExcelファイル** にまとめる形式に統一しています。

**ファイル名**: `<プロジェクト名>_試験成績書_<実施日 YYYYMMDD>.xlsx`
(例: `my-recipe_試験成績書_20260918.xlsx`)

**シート構成**:

| シート | 内容 |
|---|---|
| 1枚目 | シート名 `試験項目書_試験成績書`。試験項目と結果を**同じ行**に統合<br>(列: `No` / `試験項目` / `試験手順` / `期待結果` / `実施結果` / `判定`) |
| 2枚目以降 | 1シート1項目のエビデンス。シート名は `No` と完全一致(`TC01`, `TC02`...) |

**書式のルール**(プロジェクトが変わっても統一する):

- 見出し行: 太字、背景 `#E8ECEF`、中央揃え、枠線あり
- 通常セル: 枠線あり、上詰め、折り返し表示
- 判定列: `OK` は太字・緑(`#147A5B`)、`NG` は太字・赤(`#C1452C`)、中央揃え
- 備考・注記行: イタリック、グレー(`#7C6D59`)

💡 **なぜ形式を統一するのか。**
プロジェクトごとに書式が違うと、読む側が毎回「どこを見ればいいか」を探します。
統一されていれば、**判定列を見るだけで全体が分かります**。
個人開発でも、自分の過去の試験結果を見返すときに効いてきます。

⚠️ 試験のために本番DBへ入れたテストデータ(テスト用のレシピなど)は、
**試験終了後に削除して元の状態に戻してください。**

## 19.7 自動テストについて

ここまでは **手で操作する試験(手動試験)** の話でした。
実務では、コードで自動化することも多いです。

| 種類 | 何を試すか | 道具 |
|---|---|---|
| ユニットテスト | 関数単体 | Vitest, Jest |
| 結合テスト | 部品同士の連携 | Testing Library |
| E2Eテスト | 画面を実際に操作 | **Playwright** |

### 今回、自動テストを書かない理由

- 個人利用の小さなアプリで、試験項目が20個程度
- **AIの生成結果は毎回変わる** ので、「この文字列が出る」という検証がしにくい
- まず動くものを作る経験のほうが優先

💡 ただし、**`parseIngredients` のような純粋な関数** は自動テストに向いています。
「入力Aを与えたら必ず出力Bになる」と決まっているからです。
次に学ぶことの候補として、21章で扱います。

### Playwrightで自動操作するときの注意

デプロイ済みのアプリをPlaywrightで自動操作する場合:

- ⚠️ **操作の間に2〜4秒空ける**。連続アクセスはVercelのレート制限を誘発します
- ⚠️ 失敗しても即リトライしない(**30〜60秒空ける**)。連続リトライは状況を悪化させます
- ⚠️ **ハイドレーション**(ブラウザ側のJavaScriptが動き出すこと)の完了を待つ。
  完了前はボタンを押しても何も起きません

3つ目は、静的ファイルの読み込みが一部失敗したときに実際に起こります。
**画面は正しく見えているのに、クリックが一切効かない** という不気味な状態です。

## 19.8 この章のまとめ

- 試験は「動いた」ではなく「**何を確認したか説明できる**」ための作業
- **正常系・異常系・境界値** の3観点を必ず作る
- 期待結果は **具体的に**。「正常に動く」は禁句
- 実施する前に **項目を書き出す**
- 異常系は **意図的に壊して** 確認する(本番ではやらない)
- **NGは隠さず記録する**。試験は合格させる作業ではない
- 結果は決まった形式の **試験成績書** にまとめ、エビデンスを残す
- テストデータは **試験後に片付ける**

1つでも期待通りでなければ、それがあなたの見つけた最初のバグです。
