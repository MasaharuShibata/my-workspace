# 25. 商用利用するなら、何をやるべきか

> この章のゴール: 「自分だけが使うアプリ」と「他人にお金をもらって使わせるアプリ」の間に
> 何があるのかを一覧で把握し、着手順を決められるようになる。

⚠️ **法務・税務については概要の整理です。** 実際に事業として始める際は、
必ず専門家(弁護士・税理士)や公的機関の一次情報で確認してください。
この章は「何を調べるべきかの地図」として使ってください。

---

## 25.1 何が変わるのか — 前提の転換

my-recipe の要件定義には、こう書いてありました。

> 想定利用者: 開発者本人のみ(個人利用)。複数人での利用は想定しない

**この一行が、アプリのほぼ全てを決めていました**(08章)。
商用化とは、この一行を書き換えることです。すると芋づる式に全部が変わります。

| 前提 | 個人利用 | 商用 |
|---|---|---|
| 誰が使うか | 自分だけ | **見知らぬ他人** |
| データは誰のものか | 全部自分の | **利用者ごとに分離が必要** |
| 壊れたら | 自分が困る | **他人に損害。責任が発生する** |
| データが消えたら | あきらめる | **絶対に許されない** |
| 悪意のある利用 | 想定しない | **必ず来る** |
| コスト | 自分の財布 | **使われるほど増える。設計次第で赤字** |
| 止まったら | 後で直す | **連絡・復旧・場合によっては返金** |

⚠️ **技術的な作業より、「責任が発生する」ことのほうが本質的な変化です。**
利用規約・プライバシーポリシー・問い合わせ窓口が必要になるのはそのためです。

## 25.2 全体マップ

やるべきことを9分野に整理しました。**上から順に重要度が高い** 並びです。

| # | 分野 | 代表的な作業 |
|---|---|---|
| 1 | **契約・プラン** | Vercel Hobby → Pro など、規約上の問題を解消 |
| 2 | **認証とデータ分離** | ログイン必須化、RLSの本気設計 |
| 3 | **メール** | 送信基盤、ドメイン認証(SPF/DKIM/DMARC) |
| 4 | **法務** | 利用規約、プライバシーポリシー、特商法表記、免責 |
| 5 | **悪用・コスト対策** | レート制限、上限設定、監視 |
| 6 | **バックアップと復旧** | 自動バックアップ、**復旧訓練** |
| 7 | **監視と運用** | エラー通知、稼働監視、問い合わせ窓口 |
| 8 | **決済** | Stripe等、インボイス、返金・解約 |
| 9 | **品質** | 自動テスト、CI、アクセシビリティ |

## 25.3 ① 契約・プラン — 実は最初の関門

### ⚠️ Vercel Hobby プランは「非商用」限定

これが最も見落とされる点です。**規約違反はサービス停止の理由になります。**

| 状況 | 必要なプラン |
|---|---|
| 個人の趣味・学習・非営利 | Hobby(無料)でよい |
| **広告を載せる / 課金する / 業務で使う** | **Pro(有料)が必要** |

「無料で公開して、後から課金しよう」と考えている場合も、
**課金を始めた時点でProが必要** になります。最初から見込んでおいてください。

### Supabase

無料プランでも商用利用は禁止されていませんが、**実用上ほぼ不可能** です。

| 無料の制約 | 商用での問題 |
|---|---|
| 一定期間アクセスが無いと自動停止 | 利用者がいる時間帯に止まる可能性 |
| **自動バックアップが限定的** | **事故時にデータを戻せない** |
| サポートなし | 障害時に頼れる先がない |
| 容量・帯域の上限 | 利用者が増えたら足りない |

**有料プランへの移行が実質的な必須条件** です。

### Anthropic(Claude API)

商用利用は問題ありませんが、規模が変わります。

| 項目 | 個人利用 | 商用 |
|---|---|---|
| 月額 | 数十円 | **利用者数 × 利用回数 × 1回あたり単価** |
| レート制限 | 意識しない | **同時アクセスで上限に当たる**(429) |
| 障害時 | 後で試す | **代替や再試行の設計が要る** |

⚠️ **利用規約上の表示義務** も確認してください。
AIが生成した内容であることを利用者に示す、といった配慮が求められる場面があります。

### コスト構造を先に計算する

**これをやらずに始めると、使われるほど赤字になります。**

```
1ユーザーあたりの月間原価(概算)

  レシピ生成 20回/月 × 0.8円     = 16円
  Vercel(利用者数で按分)          =  ?円
  Supabase(同上)                  =  ?円
  メール送信                        =  ?円
  決済手数料(売上の数%)           =  ?円
  ─────────────────────────────────────
  合計                             = X円

  → 月額料金は X円 を十分に上回る必要がある
```

⚠️ **AIを使うアプリは、従来のWebサービスと原価構造が違います。**
「使われるほど儲かる」ではなく「**使われるほどコストが増える**」。
だから、**使い放題プランは危険** です。回数制限や段階課金を最初から設計に入れてください。

## 25.4 ② 認証とデータ分離

my-recipe は **ログインが無く、全員が同じデータを共有** しています。
商用では真っ先にここを変えます。

### やること

**1. ログイン機能を入れる(Supabase Auth)**

| 方式 | 特徴 |
|---|---|
| メール + パスワード | 定番。**メール送信が必須になる**(次節) |
| マジックリンク | パスワード不要。**メール送信が必須** |
| ソーシャルログイン(Google等) | 利用者が楽。メール送信の負担が減る |

💡 **最初はソーシャルログインだけにする** のも有効な判断です。
パスワードの保管・リセット・漏洩対応という重い責任を負わずに済みます。

**2. テーブルに `user_id` を足す**

```sql
alter table favorite_recipes
  add column if not exists user_id uuid references auth.users(id);
```

**3. RLSポリシーを書き換える**(← 14章の設計が効く場面)

```sql
-- 削除して作り直す
drop policy "anyone can view favorites" on favorite_recipes;

create policy "users can view own favorites"
  on favorite_recipes for select
  to authenticated
  using (auth.uid() = user_id);

create policy "users can add own favorites"
  on favorite_recipes for insert
  to authenticated
  with check (auth.uid() = user_id);   -- ⚠️ with check を忘れない(24章)

create policy "users can delete own favorites"
  on favorite_recipes for delete
  to authenticated
  using (auth.uid() = user_id);
```

⚠️ **`to authenticated` を付けて、`anon` を排除する** のが重要です。
付け忘れると、ログインしていない人にもポリシーが適用されてしまいます。

**4. 既存データの扱いを決める**

既に入っている行は `user_id` が空です。自分のIDを入れるか、消すか、決めてください。

**5. 認証のテストを必ず行う**

| 試験項目 | 期待 |
|---|---|
| ログインせずに一覧を開く | データが1件も見えない |
| **利用者Aでログインし、Bのデータを見ようとする** | 見えない |
| APIを直接叩いて他人のIDを指定 | 拒否される |

⚠️ 2番目・3番目は **必ず2アカウントを作って実際に試してください。**
「画面に出ないから安全」ではありません。**APIを直接叩かれても守られるか** が本番です。

## 25.5 ③ メール — 個人利用では要らなかったもの

**あなたが挙げたとおり、ここは商用化で確実に発生する作業です。**
そして、**技術的にも一番「知らないと詰む」分野** です。

### なぜメールが必要になるのか

| 場面 | メールの種類 |
|---|---|
| 新規登録の本人確認 | **トランザクションメール** |
| パスワードのリセット | トランザクションメール |
| マジックリンクでのログイン | トランザクションメール |
| 決済の領収書・失敗通知 | トランザクションメール |
| 退会・解約の確認 | トランザクションメール |
| 新機能のお知らせ・キャンペーン | **マーケティングメール** |

⚠️ **この2種類は、法律上の扱いがまったく違います**(後述)。

### ⚠️ 落とし穴1: Supabase 組み込みのメールは本番で使えない

Supabase Auth には、確認メールを送る機能が最初から付いています。
**が、これは開発用です。**

| 制約 | 内容 |
|---|---|
| 送信数 | **1時間あたり数通程度** の厳しい制限 |
| 送信元 | Supabaseのドメイン。あなたのサービス名ではない |
| 到達率 | **迷惑メールに入りやすい** |
| 文面 | カスタマイズの自由度が低い |

**商用では、独自のSMTP(メール送信サーバー)の設定が必須** です。

> Supabase → Authentication → **SMTP Settings** で外部サービスを登録する

### メール送信サービスを選ぶ

自前でメールサーバーを立てるのは **絶対に避けてください**(到達率の管理が専門領域です)。
専用サービスを使います。

| サービス | 特徴 |
|---|---|
| **Resend** | 開発者向け。設定が簡単。少量なら無料枠あり |
| **SendGrid** | 老舗。大規模実績。機能が豊富 |
| **Amazon SES** | 安い。ただし設定と審査(サンドボックス解除)が必要 |
| **Postmark** | トランザクションメールの到達率に定評 |

💡 個人〜小規模の商用なら **Resend** が始めやすいです。

### ⚠️ 落とし穴2: ドメイン認証(SPF / DKIM / DMARC)

**これをやらないと、送ったメールの多くが迷惑メールフォルダに入ります。**
そして利用者は「メールが届かない」と言い、あなたは原因が分かりません。

送信サービスに登録したあと、**自分のドメインのDNSにレコードを追加** します(22章)。

| 仕組み | レコード | 何を証明するか |
|---|---|---|
| **SPF** | TXT | 「このIPアドレスからの送信を、私は許可しています」 |
| **DKIM** | TXT / CNAME | 「この署名があるメールは、本物の私が送りました」 |
| **DMARC** | TXT(`_dmarc.ドメイン`) | 「SPF/DKIMが通らないメールは、こう扱ってください」 |

具体的な値は送信サービスが提示します。それを **ドメイン業者の管理画面で登録** します。

```
例(実際の値はサービスが指示するものを使う)

種別    ホスト            値
TXT     @                 v=spf1 include:_spf.例.com ~all
CNAME   xxxx._domainkey   xxxx.dkim.例.com
TXT     _dmarc            v=DMARC1; p=none; rua=mailto:report@あなたのドメイン
```

⚠️ **DMARCは、まず `p=none`(監視のみ)で始めてください。**
いきなり `p=reject`(認証失敗したら破棄)にすると、
設定ミスで **自分の正規メールが全部消えます**。
レポートを見て問題ないと確認してから、段階的に厳しくします。

💡 主要なメールサービス(Gmail等)は、一定量以上を送る送信者に対して
**SPF・DKIM・DMARCの設定や、ワンクリックでの配信停止を要件化** しています。
「昔は無くても届いた」は通用しません。

### ⚠️ 落とし穴3: 送信元アドレスの設計

| アドレス | 用途 | 注意 |
|---|---|---|
| `noreply@あなたのドメイン` | 自動送信 | ⚠️ 返信されても気づけない |
| `support@あなたのドメイン` | 問い合わせ | **受信できる状態にしておく**(MXレコードが必要) |

⚠️ **送信だけ設定して、受信を用意していない** のはよくある失敗です。
利用者は必ず返信してきます。**Reply-To に実際に読めるアドレスを設定** してください。

そして、**受信にはMXレコードの設定が別途必要** です(22章)。
送信サービスは送信専用なので、受信はGoogle Workspaceなどを別に契約します。

### ⚠️ 落とし穴4: バウンスと苦情の処理

- **バウンス** … 宛先が存在せず届かなかった
- **苦情(complaint)** … 受信者が「迷惑メール」と報告した

これらを放置して送り続けると、**送信ドメイン全体の評価が下がり、
まともなメールも届かなくなります**。

送信サービスが提供する **抑制リスト(suppression list)** を有効にして、
問題のあるアドレスへの送信を自動停止させてください。

### 法律面 — 特定電子メール法

日本で広告・宣伝を含むメールを送る場合、主に以下が求められます。

| 要件 | 内容 |
|---|---|
| **オプトイン** | 事前に同意を得た相手にのみ送る |
| **送信者の表示** | 氏名・名称、住所、問い合わせ先を記載 |
| **配信停止の方法** | 明示し、**簡単に停止できる**ようにする |
| **記録の保存** | 同意を得た記録を残す |

⚠️ **区別が重要です。**

| 種類 | 例 | 規制 |
|---|---|---|
| トランザクションメール | パスワードリセット、領収書 | 広告を含まなければ、原則この規制の対象外 |
| マーケティングメール | キャンペーン、新機能案内 | **対象。同意と配信停止が必須** |

💡 **危険なのは混ぜること** です。
領収書メールの末尾にキャンペーン広告を入れると、
そのメール全体が広告メール扱いになりえます。**分けて送るのが安全** です。

### メール作業のチェックリスト

- [ ] メール送信サービスを契約した
- [ ] SupabaseのSMTP設定に登録した
- [ ] **SPF・DKIM・DMARCをDNSに設定した**
- [ ] DMARCは `p=none` から始めた
- [ ] Reply-To に読めるアドレスを設定した
- [ ] 問い合わせ用アドレスを**受信できる**ようにした(MXレコード)
- [ ] メール文面(確認・リセット)を自社向けに書き換えた
- [ ] **実際にGmail・Yahoo・iCloud等に届くか確認した**(迷惑メール判定も含めて)
- [ ] バウンス・苦情の自動抑制を有効にした
- [ ] マーケティングメールに配信停止導線を入れた

⚠️ 下から3番目を必ずやってください。**自分のアドレスにだけ届いても意味がありません。**
複数のメールサービスで、受信箱に入るかを確認します。

## 25.6 ④ 法務 — 何を用意するか

| 文書 | いつ必要か | 概要 |
|---|---|---|
| **利用規約** | 他人に使わせるなら常に | 禁止事項、免責、解約、準拠法など |
| **プライバシーポリシー** | **個人情報を扱うなら必須** | 取得する情報、利用目的、第三者提供、問い合わせ先 |
| **特定商取引法に基づく表記** | **有料で販売するなら必須** | 事業者名、住所、連絡先、価格、支払方法、返品条件など |

### my-recipe 特有の免責事項

**レシピを提供するアプリには、固有のリスクがあります。**

- AIの生成物であり、内容の正確性を保証しない
- **アレルギー物質について保証しない**
- **食中毒・加熱不足等について責任を負わない**
- 栄養・健康上の助言ではない

⚠️ **これは形式的な話ではありません。**
「生の鶏肉を使う手順が不十分だった」といった事態は現実に起こりえます。
生成AIを使うサービスでは、**出力の性質と限界を明示する** ことが特に重要です。

### 個人情報の取り扱い

メールアドレスを取得した時点で、個人情報を扱う事業者になります。

- 利用目的を特定して公表する
- 安全管理措置を講じる(暗号化、アクセス制限)
- **本人からの開示・訂正・削除の求めに応じる体制**
- 漏洩時の報告義務

💡 **「退会したらデータを消す」機能** は、技術的にも法的にも必要になります。
設計に入れておいてください。

### 海外の利用者がいる場合

EU圏の利用者がいるならGDPR、米国カリフォルニア州ならCCPAなど、
**現地の法律が適用されうる** ことに注意してください。
最初は **日本国内限定** と規約に明記するのも、現実的な選択です。

## 25.7 ⑤ 悪用・コスト対策 — AIアプリ特有の最重要項目

**ここを飛ばすと、ある朝起きたら高額請求、という事態が起こります。**

### 何が起きうるか

```
悪意のある利用者が、あなたのAPIを自動で1秒に10回叩く
  → 1日で864,000回
  → 864,000 × 0.8円 = 約69万円
```

my-recipe の現状は **ログイン不要で誰でもレシピ生成を呼べる** ので、
理論上これが可能です。個人利用なら「URLを知られなければ大丈夫」ですが、
商用で公開したら **必ず狙われます**。

### 対策(上から順に効果が大きい)

| # | 対策 | 内容 |
|---|---|---|
| 1 | **ログイン必須にする** | 匿名で叩けなくする。最も効果的 |
| 2 | **ユーザーごとの利用回数制限** | 「1日20回まで」などをDBで記録して判定 |
| 3 | **レート制限** | 同一ユーザー/IPからの短時間の連続呼び出しを拒否 |
| 4 | **APIプロバイダ側の上限設定** | Anthropicコンソールで月間の利用上限を設定 |
| 5 | **アラート** | 使用量が閾値を超えたら通知 |
| 6 | **入力長の制限** | 食材10個の制限は既にある(コストの上限を作っている) |
| 7 | **CAPTCHA** | 自動化されたアクセスを弾く |

💡 **my-recipe が既に持っている対策** を確認してください。

- 「ボタンを押したときだけ呼ぶ」(基本設計書 5.2)
- 「食材は最大10個」(コストの上限)
- 「生成中はボタンを無効化」(二重送信防止)

**設計の時点でコストを意識していた** ので、土台はできています。
足りないのは「ログイン」と「回数制限」です。

### 利用回数の制限を実装するなら

```sql
create table usage_logs (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references auth.users(id),
  created_at timestamptz not null default now()
);

create index usage_logs_user_date_idx on usage_logs (user_id, created_at desc);
```

レシピ生成の前に「この利用者の今日の回数」を数え、上限を超えていたら拒否します。

⚠️ **この判定は必ずサーバー側で行ってください。**
ブラウザ側のカウントは書き換えられます(12章の原則)。

## 25.8 ⑥ バックアップと復旧

**「バックアップがある」と「復元できる」は別の話です。**

| やること | 内容 |
|---|---|
| 自動バックアップ | Supabaseの有料プランで日次バックアップ |
| **PITR**(特定時点への復元) | 「3時間前の状態」に戻せる。追加オプション |
| **復旧訓練** | ⚠️ **実際に復元してみる**。年に1回は必ず |
| 手元へのエクスポート | 定期的にダンプを別の場所へ保存 |

⚠️ **復旧訓練をやっていないバックアップは、無いのと同じです。**
いざというとき「手順が分からない」「復元したら壊れていた」となります。

💡 誤操作対策としては、**論理削除**(`deleted_at` 列を立てるだけで物理削除しない)も
有効です。ただしデータ削除要求への対応(25.6)とは矛盾しうるので、
**運用ルールとセットで設計** してください。

## 25.9 ⑦ 監視と運用

個人利用では「使ってみて気づく」で済みました。商用では**気づく仕組み**が要ります。

| 項目 | 手段 |
|---|---|
| **エラー通知** | Sentry等のエラー監視。例外が起きたら通知が飛ぶ |
| **稼働監視** | 外部から定期的にアクセスし、落ちたら通知 |
| **利用状況** | アクセス解析。どこで離脱しているか |
| **コスト監視** | Anthropic / Vercel / Supabase の使用量アラート |
| **ログの保全** | 障害時に追跡できる期間の確保 |

### 問い合わせ窓口

**必須です。** 規約・特商法表記にも連絡先を書く必要があります。

- 専用のメールアドレス(**受信できること**。25.5参照)
- 返答の目安時間を明示
- よくある質問(FAQ)を用意して、問い合わせ自体を減らす

### 環境を分ける

```
本番環境    利用者が使う。Supabase本番プロジェクト + Vercel Production
ステージング 本番と同じ構成で試す。別のSupabaseプロジェクト
開発環境    手元。ローカル
```

⚠️ **本番のデータベースで試すのをやめる**、というのが商用化の大きな区切りです。
19章で「テストデータは試験後に削除する」と書きましたが、
商用では **そもそも本番で試験しない** 体制にします。

## 25.10 ⑧ 決済

有料化するなら、決済代行サービスを使います。

⚠️ **クレジットカード情報を自分のサーバーで扱ってはいけません。**
PCI DSSという厳しい基準への準拠が必要になります。
**Stripe等に任せ、自分のサーバーにはカード情報を通さない** のが鉄則です。

| 検討項目 | 内容 |
|---|---|
| 課金モデル | 月額 / 従量 / 回数券。**AIコストがあるので使い放題は危険** |
| 無料枠 | どこまで無料で使わせるか |
| 失敗時の処理 | カード期限切れ、残高不足 |
| **解約・返金** | 規約に明記。途中解約の扱い |
| **請求書・領収書** | インボイス制度への対応 |
| 税 | 消費税の扱い。売上規模による |

💡 決済状態(有効/停止)は **Webhookで受け取ってDBに反映** します。
23章で学んだWebhookが、ここでも出てきます。

## 25.11 ⑨ 品質

| 項目 | 個人利用 | 商用 |
|---|---|---|
| 試験 | 手動20項目 | **自動テスト + 手動** |
| CI | 無し | **pushのたびに自動でテスト実行** |
| 型チェック | ローカル | CIで必須化 |
| アクセシビリティ | 気をつける | **対応が求められる場面がある** |
| 表示速度 | 気にしない | 離脱率に直結 |

### CIを入れる

GitHub Actions で、pushのたびに以下を自動実行します。

```
npm ci
npm run lint
npx tsc --noEmit      ← 型チェック
npm test              ← 自動テスト
npm run build
```

⚠️ **これが通らないとマージできない** ようにすると、
「壊れたコードが本番に出る」ことが構造的に防げます。

## 25.12 着手順 — 現実的なロードマップ

全部を一度にやるのは不可能です。段階を切ります。

### フェーズ0: 公開する前(必須)

- [ ] **Vercel Pro へ移行**(規約上の要件)
- [ ] **Supabase 有料プランへ移行**(バックアップのため)
- [ ] **ログインを実装し、RLSを user_id ベースに書き換える**
- [ ] **他人のデータが見えないことを、2アカウントで実地確認**
- [ ] **メール送信基盤 + SPF/DKIM/DMARC**
- [ ] **利用回数制限とレート制限**(コスト防衛)
- [ ] 利用規約・プライバシーポリシー・免責
- [ ] 問い合わせ窓口(受信できるメールアドレス)
- [ ] エラー監視とコストアラート

### フェーズ1: 公開直後

- [ ] 特商法表記(有料化する場合)
- [ ] 決済
- [ ] バックアップからの**復旧訓練**
- [ ] ステージング環境
- [ ] FAQ

### フェーズ2: 育ってきたら

- [ ] 自動テストとCI
- [ ] 退会・データ削除機能
- [ ] アクセス解析に基づく改善
- [ ] リージョン最適化、性能改善

⚠️ **フェーズ0を飛ばして公開しないでください。**
特に「ログインとRLS」「メール」「コスト防衛」の3つは、
**後から追加するのが最も大変で、事故が起きたときの被害が最も大きい** 項目です。

## 25.13 個人利用のまま、少しだけ他人に見せたい場合

「商用ではないが、友人に見せたい」という中間のケースもあります。
その場合は、フル装備は要りません。

| やること | 理由 |
|---|---|
| **Vercelの Deployment Protection**(パスワード保護) | URLが漏れても入られない |
| 利用回数の制限、または一時的な公開 | コスト防衛 |
| 「試作品である」ことの明示 | 期待値の調整 |
| 見られて困るデータを入れない | 最も確実な対策 |

💡 **「アクセスを絞る」だけで、多くの問題が消えます。**
認証・規約・監視が必要になるのは「不特定多数に開く」からです。
**開く範囲を小さく保つ** のは、立派な設計判断です。

## 25.14 この章のまとめ

- 商用化の本質は技術ではなく、**責任が発生すること**
- ⚠️ **Vercel Hobbyは非商用限定**。まずここを確認する
- Supabase無料プランは **バックアップが無い**ので商用では実質使えない
- **ログイン + RLSの user_id 化** が最優先。**APIを直接叩いても守られるか**まで試験する
- **メールは専用サービス + SPF/DKIM/DMARC が必須**。組み込みSMTPは開発用
- **DMARCは `p=none` から段階的に**
- トランザクションメールとマーケティングメールを **混ぜない**
- 利用規約・プライバシーポリシー・特商法表記・**免責(アレルギー等)**
- ⚠️ **AIアプリは使われるほどコストが増える**。ログイン必須 + 回数制限で守る
- **復旧訓練をやっていないバックアップは、無いのと同じ**
- 全部いっぺんにやらない。**フェーズ0だけは飛ばさない**

## 25.15 最後に

ここまでの内容を見て「多すぎる」と感じたなら、それは正しい感覚です。

**個人利用のアプリを作るのと、サービスを運営するのは、別の仕事です。**
前者は数日でできますが、後者は継続的な責任を伴います。

だからこそ、**まず個人利用のものを完成させた** ことに意味があります。
土台があるから、ここに何を足せばいいかが具体的に見えている。
ゼロから「商用サービスを作るぞ」と始めた人には、この地図は描けません。

そして、この章の項目のうち、
**「これは要らない」と判断して外すことも、また設計です**(08章)。
全部やるのが正解ではなく、**自分のサービスに必要なものを選ぶ**。

その判断ができるようになっていれば、この教材の目的は達成されています。
