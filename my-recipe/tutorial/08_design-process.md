# 08. 設計 — 作り始める前に何を決めるか

> この章のゴール: 真っ白な状態から「作れる状態」までを、自分の手で埋められるようになる。

コードは書きません。**ここがこの教材で一番大事な章です。**

初心者がアプリを作れない理由は、文法を知らないからではありません。
**何を作るのか決まっていないまま書き始めるから** です。

---

## 8.1 なぜ設計するのか

「思いついたものを作りながら決めればいい」で進むと、こうなります。

```
「レシピアプリ作るぞ」
  → とりあえず画面を作る
  → あ、ログイン要る? → 後から入れるの大変だ…
  → お気に入り保存しよう → DBの列、何にする?材料って配列?文字列?
  → 一覧に絞り込みほしい → ジャンル?保存してない…DBの作り直しだ
  → 作り直すとデータが消える…
```

これは「手が遅い」のではなく **決める順番が逆** なだけです。

設計は、**手を動かす前に紙の上で失敗しておく作業** です。
コードで失敗すると半日かかりますが、紙の上なら5分で直せます。

### 3段階に分ける

| 段階 | 答える問い | 粒度 |
|---|---|---|
| **要件定義** | 何を・誰のために作るのか | 日本語だけ。技術の話は出さない |
| **基本設計** | どういう構成で実現するか | 画面一覧・技術選定・DBの全体像 |
| **詳細設計** | 中身をどう作るか | ファイル構成・関数・列定義 |

**上から順に決める** のがポイントです。
「Next.jsを使うぞ」から始めてはいけません。それは基本設計の話であって、
その前に「何を作るか」が決まっていないと、選ぶ理由が無いからです。

my-recipe の `docs/` は、まさにこの3段階に分かれています。

---

## 8.2 要件定義 — 何を作るか

### ① 目的を1〜2文で書く

これが書けなければ、作ってはいけません。

> 手元にある食材をいくつか入力するだけで、AIがそれらを活かしたレシピを考案してくれる
> レシピ提案アプリを提供する。気に入ったレシピはお気に入りとして保存し、あとから見返せるようにする。

コツは **「誰が、どんなときに、何ができるようになるか」** を含めることです。

### ② 背景 — なぜ作るのか

> 「冷蔵庫にある食材で何が作れるか思いつかない」という悩みを、AIによるレシピ考案で解決する。

背景が書いてあると、後で迷ったとき判断できます。
たとえば「レシピを検索する機能も付ける?」と思いついたとき、
背景に立ち返れば「**検索サイトとは違うものを作る**と決めたはずだ」と却下できます。

### ③ 想定利用者

> 開発者本人のみ(個人利用)。複数人での利用は想定しない

**これが一番効く一行です。** ここが決まると、芋づる式に決まります。

| 「個人利用のみ」から導かれること |
|---|
| ログイン機能が要らない → 画面が2つ減る、DBの設計が単純になる |
| `user_id` 列が要らない → テーブルがシンプルになる |
| 同時アクセス数を考えなくていい → 無料プランで足りる |
| デザインを万人向けにしなくていい |

⚠️ 逆に「将来みんなに使ってもらうかも」と考え始めると、
ログイン・権限・通報機能…と際限なく膨らみ、**永遠に完成しません**。
初心者の最初のアプリは、**利用者を自分1人に絞る** のが正解です。

### ④ 機能を書き出して、MUST / WANT に分ける

思いつく機能を全部書き出してから、必ずランク付けします。

| # | 機能 | 区分 |
|---|---|---|
| F1 | 食材の入力 | **MUST** |
| F2 | AIによるレシピ考案 | **MUST** |
| F3 | レシピ結果の表示 | **MUST** |
| F4 | お気に入り登録 | WANT |
| F5 | お気に入り一覧表示 | WANT |
| F6 | お気に入り削除 | WANT |
| F7 | ジャンル選択 | WANT |
| ... | ... | ... |

**MUST = これが無いとアプリとして成立しないもの。**

my-recipe の MUST は F1〜F3 の3つだけです。つまり
**「食材を入れたらレシピが出る」だけ作れば、いったん完成** です。
お気に入りすら WANT です。

この区別が、製造の順番をそのまま決めます。**MUSTから作る。**
WANTは後回しにして、時間が無ければ落とす。それができるように最初に分けておきます。

🖐 あなたが作りたいアプリで、MUSTを3つ以内に絞れますか?
4つ以上ある場合、たぶんまだ絞れていません。

### ⑤ やらないことを、はっきり書く

**要件定義で一番大事なのは、実はここです。**

> ### 対象外(スコープ外)とする機能
> - ログイン・ユーザーごとのデータ分離
> - お気に入り登録していない生成結果の履歴保存
> - 生成されたレシピの手動編集
> - カロリー・栄養素の計算
> - 1回の検索で複数のレシピ候補を提示する機能
> - レシピ画像の生成

なぜこれを書くのか。**作っている最中に必ず「あれもできそう」と思うから** です。
そのとき、ここに書いてあれば「今回はやらないと決めた」と即断できます。
書いていないと、毎回悩み、そして手を出して、完成が遠ざかります。

💡 「やらない」ではなく「**今回はやらない**」と考えてください。
捨てるのではなく、次のバージョンに送るだけです。

### ⑥ 非機能要件 — 「動く」以外の条件

機能ではないけれど決めておくべきことです。

| 観点 | my-recipeでの決定 |
|---|---|
| **コスト** | Vercel・Supabaseは無料枠。**Claude APIは従量課金**で1回1円未満 |
| **可用性** | 24時間動く保証は不要。DBが自動停止しても手動再開でよい |
| **セキュリティ** | ログイン無し。**URLを知る人は誰でも読み書きできることを許容する** |
| **保守性** | 設計書を整備する。環境構築手順を全部文書化する |

セキュリティの項が重要です。ここには
**「安全です」ではなく「ここが危険だが、この理由で受け入れる」** と書かれています。

> デプロイ後のURLとSupabaseのanonキーを知っていれば誰でもお気に入りを閲覧・登録・削除できる
> ことを明確な制約として受け入れる

これが正しい書き方です。リスクを知らずに作るのと、
知ったうえで許容するのは、まったく違います。
そして代替案(Vercelのパスワード保護)まで書いてあるので、
後から気が変わったときの道も残っています。

### ⑦ コストを見積もる ← 外部APIを使うなら必須

AIを使うアプリでは、**使うほどお金がかかります**。
作る前に「1回いくらか」を計算してください。

```
Claude Haiku 4.5: 入力 $1.00 / 出力 $5.00 (各100万トークンあたり)

1回のレシピ考案:
  入力  約600トークン  = 600 / 1,000,000 × $1.00 = $0.0006
  出力 約1000トークン  = 1000 / 1,000,000 × $5.00 = $0.0050
  合計 約 $0.0056 ≒ 0.8円
```

💡 **トークン**とは、AIが文章を処理する単位です。
日本語だとだいたい1文字1〜2トークンくらい、と思っておけば見積もりには足ります。

この試算があるから、
「1日10回使っても月30円以下」→ **個人利用なら気にしなくていい** と判断でき、
同時に「10個までの食材制限を付けよう」という設計にもつながります。

⚠️ 見積もりが「月1万円」になるなら、そもそも作り方を変えるべきです。
**作ってから気づくと、もう遅い。**

## 8.3 基本設計 — どういう構成で作るか

要件が決まったら、実現手段を決めます。

### ① 構成図を描く

登場人物と、その間のやりとりを図にします。手書きで十分です。

```
ブラウザ ──HTTPS──> Vercel(Next.js) ──> Claude API
                          │
                          └──> Supabase(DB)
```

図を描く価値は、**「誰が誰を呼ぶか」が固定される** ことです。
ここで「ブラウザ → Claude API の矢印は引かない」と決めたことが、
そのまま実装の制約になります。

### ② 技術を選ぶ — 理由とセットで

| 分類 | 採用 | 理由 |
|---|---|---|
| フロント/バック | Next.js + TypeScript | 画面とサーバー処理を1プロジェクトで書ける |
| ホスティング | Vercel | GitHubにpushするだけで自動デプロイ。個人利用は無料 |
| DB | Supabase | 無料でPostgreSQLとRLSが使える |
| AI | Claude API (Haiku 4.5) | 単純なテキスト生成なので最も安価なモデルで足りる |

⚠️ **「流行っているから」は理由になりません。**
「何を優先した結果その選択になったのか」を書いてください。
ここに書いた理由が、後で技術を乗り換えるときの判断材料になります。

### ③ 画面を洗い出す

機能一覧(F1〜F12)を眺めて、**どの画面でそれを使うか** を割り振ります。

| # | 画面名 | パス | 担当する機能 |
|---|---|---|---|
| S1 | ホーム(レシピ検索) | `/` | F1〜F4, F7〜F9, F12 |
| S2 | お気に入り一覧 | `/favorites` | F5, F6, F10, F11 |

my-recipe は **たった2画面** です。
「レシピを作る場所」と「保存したものを見る場所」。これ以上分ける理由がありません。

⚠️ 初心者は画面を増やしすぎます。
「レシピ詳細画面」を作りたくなりますが、一覧の中で開閉すれば足ります(F10)。
**画面を1つ増やすと、遷移・戻る・URL設計・状態の受け渡しが全部増えます。**

### ④ 画面遷移図

```
S1 ホーム  ──ヘッダーの「お気に入り」──>  S2 お気に入り一覧
   <──────ヘッダーの「ホーム」────────
```

行き止まりが無いか、戻れない画面が無いかを確認します。

### ⑤ 各画面に何を置くか

S1(ホーム)を上から順に:

1. 食材入力欄
2. ジャンル選択
3. 「レシピを考えてもらう」ボタン
4. 生成結果(未生成時は非表示)
5. 「お気に入り登録」「別のレシピを提案してもらう」ボタン

**紙に手書きのワイヤーフレーム(枠だけの絵)を描くと、ここが一気に進みます。**
きれいに描く必要はありません。四角と文字だけで十分です。

### ⑥ データベースの全体像を決める

**ここが設計の山場です。** 考える順番があります。

#### 手順1: 「保存する必要があるもの」だけを挙げる

- 生成されたレシピ → **保存しない**(お気に入り登録されたものだけ)
- お気に入りレシピ → **保存する**
- 入力した食材 → 保存しない(お気に入りの一部としてなら保存する)
- 材料のチェック状態 → **保存しない**(調理中だけの一時的なもの)

**「保存しない」を明確にするのが大事です。** 何でも保存すると、
テーブルが増え、消す処理が増え、個人情報の管理まで発生します。

結果、テーブルは **`favorite_recipes` の1つだけ** になりました。

#### 手順2: 1行が何を表すか決める

> 1行 = お気に入り登録されたレシピ1件

この一文が言えないテーブルは、設計を間違えています。

#### 手順3: 必要な列を、画面から逆算する

「お気に入り一覧画面に表示したいもの」を見ながら列を決めます。

| 画面に出したいもの | 列 |
|---|---|
| 料理名 | `title` |
| ジャンル(絞り込みにも使う) | `genre` |
| 調理時間 | `cooking_time` |
| 何人分 | `servings` |
| どの食材で作ったか | `source_ingredients` |
| 材料 | `ingredients` |
| 作り方 | `steps` |
| 新しい順に並べたい | `created_at` |
| 削除時に1件を特定したい | `id` |

**画面に出ないものは、列にしない。** これが列を増やしすぎないコツです。

#### 手順4: 型を決める(ここに設計判断が出る)

材料は「鶏むね肉 200g」「白菜 1/4個」…と複数あります。どう保存するか?

| 案 | 内容 | 評価 |
|---|---|---|
| A | 別テーブル `ingredients` を作って1材料1行 | 正統派だが、テーブルが3つに増え、JOINが必要になる |
| B | `jsonb` 型で配列のまま保存 | 柔軟だが、初心者には扱いが難しい |
| C | **改行区切りの1つのtext** | 単純。表示時に `split("\n")` するだけ |

my-recipe は **C** を選びました。理由は明快です。

- 材料を個別に検索・集計する要件が **無い**
- 常に「レシピ1件まるごと」でしか使わない
- 他のプロジェクト(kakeibo)と書き方を揃えられる

⚠️ **「正しい設計」ではなく「この要件に合う設計」を選ぶ** のが設計です。
もし将来「にんじんを使うレシピを検索」という要件が出たら、Aに変えるべきです。
そのときは、そう判断した記録(設計書)があるので、迷わず変えられます。

### ⑦ 非機能の設計

要件定義で決めた方針を、具体的な手段に落とします。

| 要件 | 設計 |
|---|---|
| APIキーを漏らさない | `NEXT_PUBLIC_` を付けない環境変数 + Route Handlerからのみ呼ぶ |
| コストを抑える | ボタンを押したときだけAPI呼び出し。食材は最大10個 |
| ログイン無しでも将来拡張したい | RLSを**無効化せず**、「anonに常に許可」ポリシーにする |

3つ目が味わい深い判断です。RLSを無効にしても動きますが、
**「常に許可」というポリシーを明示的に書いておけば、将来ログインを足すときに
条件式を差し替えるだけで済みます**。今の手間は同じで、将来の手間が減る。

## 8.4 詳細設計 — 中身をどう作るか

基本設計が「何を作るか」なら、詳細設計は「どう書くか」です。
**ここまで書けていれば、実装は作業になります。**

### ① ディレクトリ構成を決める

```
my-recipe/
├── app/
│   ├── layout.tsx                     # 共通レイアウト
│   ├── globals.css                    # 共通スタイル
│   ├── page.tsx                       # S1: ホーム
│   ├── favorites/page.tsx             # S2: お気に入り一覧
│   ├── actions.ts                     # Server Actions(登録・削除)
│   └── api/generate-recipe/route.ts   # Route Handler(AI呼び出し)
├── components/                        # 画面部品
├── lib/                               # 共通処理・型定義
├── supabase/schema.sql                # テーブル定義
└── docs/                              # 設計書
```

考え方はシンプルです。

- `app/` … URLになるもの
- `components/` … 画面の部品
- `lib/` … 画面ではないもの(型・外部サービスとの接続)

💡 詳細設計書には **「作らないファイル」も書かれています**。

> ログイン機能を持たないため、`middleware.ts`・`app/login/`・`lib/supabase/client.ts` は作成しない

これがあると、後で読んだ人が「なぜ無いのか」で悩みません。

### ② コンポーネントに分解する

画面を部品に割ります。**各部品に「何を受け取って、何を表示するか」を書きます。**

| 部品 | 受け取るもの | 役割 |
|---|---|---|
| `Header` | なし | ナビゲーション |
| `IngredientForm` | `generating`, `onSubmit` | 入力とバリデーション |
| `RecipeResult` | `recipe`, `genre`, `onRegenerate` … | 生成結果の表示 |
| `FavoriteList` | `favorites`, `filtered` | 一覧(0件時のメッセージも担当) |
| `FavoriteCard` | `favorite` | 1件の開閉・削除 |
| `GenreFilter` | `selected` | 絞り込みリンク |

### ③ stateをどこに置くか決める

06章で扱った話です。詳細設計書 2.1 にはこう書かれています。

> `IngredientForm.tsx`は入力中の食材文字列・選択中のジャンル・入力バリデーションエラーのみを
> ローカルで管理し、送信時に`onSubmit(ingredients, genre)`を呼ぶだけの構成にする。
> こうすることで、`RecipeResult.tsx`の「別のレシピを提案してもらう」ボタンからも、
> `IngredientForm.tsx`を経由せず同じ生成処理を呼び出せる

**「こうすることで〜できる」という形で書かれている** のがポイントです。
判断には必ず理由を書く。理由の無い決定は、後で誰も変えられなくなります。

### ④ 入出力の形を決める

APIの入口と出口を、JSONの形で確定させます。

```
リクエスト(ブラウザ → 自分のサーバー)
POST /api/generate-recipe
{ "ingredients": ["鶏むね肉","白菜"], "genre": "和食", "avoidTitle": "生姜炒め" }

レスポンス(成功)
{ "recipe": { "title": "...", "cookingTime": "...", "servings": "...",
              "ingredients": ["..."], "steps": ["..."] } }

レスポンス(失敗)
{ "error": "食材を1つ以上入力してください。" }   ステータス 400 または 500
```

**この形が決まれば、画面側とサーバー側を別々に作れます。**
これは13章で「先に偽のレシピを返すAPIを作る」という進め方に直結します。

### ⑤ バリデーション(入力チェック)を決める

| チェック | メッセージ | どこで |
|---|---|---|
| 空でないか | 食材を1つ以上入力してください。 | ブラウザ + **サーバー** |
| 10個以内か | 食材は10個までにしてください。 | ブラウザ + **サーバー** |

⚠️ **両方に書く** のが正解です。
- ブラウザ側 … 利用者にすぐ知らせるため(親切心)
- サーバー側 … 不正なデータを防ぐため(**安全のため**)

ブラウザのチェックは利用者に消せるので、安全の役には立ちません。

### ⑥ エラー処理を決める

「どこで失敗しうるか」を列挙して、それぞれの見せ方を決めます。

| 失敗 | 返すもの | 画面表示 |
|---|---|---|
| 食材が空/多すぎ | 400 | 入力欄の下に赤字 |
| Claude API呼び出し失敗 | 500 | 「レシピの考案に失敗しました。もう一度お試しください。」 |
| 返ってきたJSONの形が違う | 500 | 同上 |
| DB登録失敗 | `{ error: "..." }` | ボタンの近くに赤字 |

⚠️ 利用者に見せるメッセージに、**技術的な詳細を書かない** こと。
「TypeError: cannot read property」と出されても利用者は困ります。
「もう一度お試しください」と、**次にどうすればいいか** を書きます。

### ⑦ AIへの指示(プロンプト)を設計する

AIを使うアプリ特有の設計項目です。これも設計書に書きます。

```
システムプロンプト(役割と制約):
  あなたは家庭料理のレシピを考案する料理アシスタントです。
  与えられた食材を活かした、家庭で作りやすい料理のレシピを1つ考案してください。
  塩・こしょう・醤油・油などの基本的な調味料は、リストに無くても使って構いません。
  調理時間(目安)と人数(何人分)も必ず出力してください。
  出力は指定された形式のみとし、それ以外の説明文は含めないでください。

ユーザーメッセージ(毎回変わる部分):
  (ジャンルは「和食」の料理にしてください。)
  (直前に提案した「○○」とは別の料理を考えてください。)
  次の食材を使ったレシピを考えてください: 鶏むね肉、白菜
```

設計のポイントが3つあります。

1. **変わらない指示(役割・制約)はシステムプロンプトへ**、
   毎回変わる情報(食材)はユーザーメッセージへ
2. 「基本調味料は使ってよい」のような **暗黙の前提を明文化** する。
   書かないと「塩が無いので味付けできません」のような返事が来ます
3. **出力の形を固定する**(後述の構造化出力)

### ⑧ 既知の制約を書き残す

詳細設計書の最後に、こういう節があります。

> - 生成結果の再現性は無い。同じ食材でも毎回違うレシピが返る
> - お気に入りの編集機能は無い
> - 材料のチェック状態は保存されない
> - 列を追加した際は、既存環境に `ALTER TABLE` を個別に適用する必要がある

**バグではなく仕様である**ことを書いておく場所です。
これが無いと、半年後の自分が「バグだ」と思って直そうとします。

## 8.5 まとめ — 設計チェックリスト

新しいアプリを作るとき、この順に埋めてください。

**要件定義**
- [ ] 目的を1〜2文で言えるか
- [ ] 想定利用者は誰か(**1人に絞れないか?**)
- [ ] 機能を書き出し、MUSTを3つ以内に絞ったか
- [ ] **やらないこと**を明記したか
- [ ] コストは見積もったか(外部APIを使うなら必須)
- [ ] セキュリティ上の妥協点を、**自覚して**書いたか

**基本設計**
- [ ] 構成図を描いたか(誰が誰を呼ぶか)
- [ ] 技術選定に**理由**を書いたか
- [ ] 画面は何枚か(**増やしすぎていないか**)
- [ ] 保存するもの/しないものを分けたか
- [ ] テーブルの「1行が何か」を言えるか
- [ ] 列は画面から逆算したか

**詳細設計**
- [ ] ディレクトリ構成を決めたか
- [ ] コンポーネントに分けて、受け渡すものを決めたか
- [ ] APIの入出力JSONを確定したか
- [ ] バリデーションを**ブラウザとサーバーの両方**に置いたか
- [ ] エラー時に何を表示するか決めたか
